# P31.4 — Production Worker Forensics: False Stall, Stale Status, and NOT_FOUND

Date: 2026-10-17
Scope: determine why a 10-scene mock production run appeared stuck at
`20 completed / 1 waiting`, why `scene_render` seemed never to start, and why
`get_run_status` returned `NOT_FOUND` after roughly 30 seconds.
Status: recon-only. No production code changed. No commit or push.

## Verdict

The scheduler and render worker are not stuck. The run continues through
`scene_render` and `final_compose`, and it can complete successfully.

The observed behaviour is an observability and lifecycle problem:

1. **Progress is only published at iteration boundaries.** During a whole
   `scene_render` batch, the persisted and returned summary stays at
   `completed: 20`, `running: 0`, `waiting: 1`, even while renders are actively
   starting and finishing. That is exactly the Hermes snapshot.
2. **Run status is served from an in-memory registry that is not shared by all
   Next.js route instances.** A status route can import a run once and then
   serve that frozen snapshot forever.
3. **Recovery only runs when a service instance is constructed.** A warm status
   worker that existed before the run started never imports the new run and can
   return `NOT_FOUND` permanently.
4. **The run is not persisted before the start response returns.** A status
   request in the first ~150 ms can therefore hit another registry instance with
   no run and receive `NOT_FOUND`, even though the start call returned `202`.

The Hermes `scene_render` conclusion was based on status summaries, not the run
event log. In the live reproduction the first `scene_render` started four
seconds after the run started, and the event log recorded every render.

## Code paths

### 1. A separate service instance per route graph

`lib/production/run-service.ts:1149` exports a module-level singleton:

```ts
export const headlessProductionRunService = new HeadlessProductionRunService(
  buildDefaultConfig(),
  {},
  {
    runStore: new FileRunStore(),
    autoRecover: autoRecoverEnabled()
  }
);
```

Next.js route handlers do not guarantee that this module instance is shared
across compiled route graphs. The start route, status route, and log route can
therefore each hold a different `HeadlessProductionRunService` and a different
`InMemoryRunRegistry`. The live test confirms this: at the same moment the
status route reported `completed: 0` while the persisted file reported `20`.

### 2. Status and log read only the local registry

`app/api/production-runs/[runId]/route.ts:18` and
`app/api/production-runs/[runId]/log/route.ts:53` call
`headlessProductionRunService.getRun(runId)`.

`lib/production/run-service.ts:382` does no store lookup:

```ts
getRun(runId: string): HeadlessRunSnapshot {
  const value = this.registry.getRun(runId);
  if (!value) {
    throw this.notFoundRunError(runId);
  }
  return value;
}
```

If this route instance has not imported the run, the result is `NOT_FOUND` even
though a valid run file exists on disk.

### 3. Recovery only happens at construction

`lib/production/run-service.ts:296` starts recovery once:

```ts
if (options.autoRecover && this.runStore) {
  void this.recoverRuns().catch(() => {});
}
```

There is no periodic recovery and no lazy recovery on status/log reads.
`recoverRuns()` (`:406`) imports all entries once. A worker constructed before a
new run exists will never see that run.

If the run already exists in the local registry, `InMemoryRunRegistry.importRun()`
is a no-op (`lib/production/run-registry.ts:153`), so a second `recoverRuns()`
does not refresh a stale snapshot. There is also no timestamp/event-count
comparison against the persisted file.

### 4. A live lock leaves the observer with the imported snapshot

When recovery sees a non-terminal run, it checks the execution lock
(`lib/production/run-service.ts:536`). If another process owns the lock, it
returns the imported snapshot without scheduling anything:

```ts
if (this.runStore?.isExecutionLocked && (await this.runStore.isExecutionLocked(entry.projectId, runId))) {
  return this.registry.getRunUnsafe(runId);
}
```

That is correct for avoiding duplicate execution, but it also means the observer
never learns that the owner has progressed, completed, or died. It has no refresh
path.

### 5. Start returns before the first persistence

`lib/production/run-service.ts:273` sets a 150 ms persistence debounce. The run
is created and the start response is returned before `flushRun()` completes.
`run-service.ts:481-489` schedules the first save.

In the live 10-scene test the run file did not exist at +2 s, and the status
route returned `404 Run not found...`. It existed by +3 s. This is a direct
start/status race, not evidence that the run was lost.

### 6. Progress is frozen during an action batch

`lib/production/production-runner.ts:377` calls `onProgress` before executing
the ready actions. For the render iteration the summary is therefore:

- `completed`: 20 (stock and narration from the previous iteration);
- `waiting`: 1 (`final_compose`);
- `running`: 0 (no render has been recorded as running yet).

The render actions are then started inside `executeBounded`
(`production-runner.ts:446`). `runningActionIds.add()` happens at `:447`, but no
progress callback is made. Completion events and `completedActionIds` are only
applied after `executeBounded` returns all results (`production-runner.ts:465`).
With `scene_render` concurrency 1, all 10 renders execute before a single
completion is published.

`lib/production/run-service.ts:792` maps only that iteration-level progress into
the registry, and `:809` writes the final batch result after the whole loop.

Consequences:

- `running` stays `0` while a render is actually running;
- `completed` stays `20` until every render in the batch is done;
- `get_run_status` looks identical for the entire render phase;
- the user sees `20 completed / 1 waiting / 0 running` and reasonably concludes
  the worker is stuck.

The event log is more accurate, but `get_run_status` does not include events.
`get_run_log` would have shown `action_started scene_render` immediately.

## Why the Hermes run looked stuck

The sequence is consistent with the code and the reproduction:

1. `run_production` returned a queued run.
2. Stock selection and narration completed quickly: 20 actions.
3. The planner marked 10 `scene_render` actions ready and `final_compose`
   waiting.
4. `onProgress` published `20 completed / 1 waiting / 0 running`.
5. The runner started renders sequentially. The first render started within
   seconds, but the summary did not change until all renders completed.
6. A status request hit either:
   - a status route instance that had imported the run while it was at the
     plateau and never refreshed it; or
   - a warm worker that had been constructed before the run and therefore did
     not know it, producing `NOT_FOUND`.
7. The composition was checked after roughly 25 seconds, while renders were
   still running. It was correctly not available yet.

Nothing in this sequence requires a scheduler failure. In the independent
10-scene reproduction the exact same shape completed successfully after the
render phase and a multi-minute composition.

## Recovery behaviour is functional

During the 10-scene test the dev server was terminated while `final_compose` was
running. The persisted run remained `running`, with a stale lock file.

After restarting the server:

- the stale lock (dead PID) was reclaimed;
- recovery imported the run and scheduled it again;
- the already-completed 30 actions were not re-executed;
- `final_compose` ran again;
- the run completed with 31 actions;
- the final composition was valid H.264/AAC, 60.038 s, 1920x1080.

So the durable store, lock reclamation, and interrupted-generation reconciliation
work for the restart case. The defect is that status/log reads do not use the
durable store to refresh or discover runs, and recovery is not triggered outside
construction.

## Secondary observations

- During composition, multiple FFmpeg processes were active at once. `dmesg`
  recorded an OOM kill of one FFmpeg process while memory use was about 7.1 GiB
  of 7.9 GiB. The recovered composition still succeeded, but composition on this
  host is resource-sensitive and should be treated as a separate reliability
  risk.
- An interrupted composition left a 48-byte `final-composition_*.mp4` file.
  The completed run wrote a separate valid composition and linked only that one
  in `project.compositions`. Orphaned intermediate artifacts are a separate
  cleanup concern.
- The status route's stale snapshot can survive indefinitely because
  `InMemoryRunRegistry.sweepExpired()` skips `queued` and `running` runs
  (`lib/production/run-registry.ts:86`). A frozen `running` snapshot is never
  evicted by retention.

## Recommended minimal fix

No fix was applied in this recon task. The smallest safe set, in priority order:

1. **Persist before returning from start.** After `createRun`, await
   `flushRun(runId)` before returning `202` (or return a retryable
   `starting` status). This removes the immediate post-start `NOT_FOUND` race.
2. **Add read-through refresh to status and log.** If the local registry has no
   run, load the persisted run by `runId`; if the local run is non-terminal,
   refresh it from the store. This requires a store lookup by `runId` (a run
   index, or a persisted `runId -> projectId` mapping) and a merge rule that
   prefers the copy with more events/newer status. A separate async
   `getRunForRead()` avoids changing the synchronous owner-side API.
3. **Publish progress per action.** Update `running` when an action starts and
   `completed` when it settles, instead of waiting for the whole action-type
   batch. Include at least the current action/scene and the log cursor in the
   status response. This removes the false `20 / 1 / 0` stall signal.
4. **Recover lazily or periodically.** When a non-terminal persisted run has no
   live execution lock, allow a status/log read or a periodic sweep to enqueue
   it. This covers workers constructed before the run, owner death after an
   observer imported the run, and long-lived warm route instances.
5. **Make `NOT_FOUND` precise.** Distinguish "run is not persisted yet" from
   "run was previously known and is genuinely lost". Do not use the
   "expired from memory or lost after a process restart" message for a run that
   was just accepted with `202`.

Suggested tests for the fix:

| Scenario | Expected |
| --- | --- |
| Status immediately after start | no `NOT_FOUND`; either `202 starting` or the queued run |
| Warm observer constructed before run start | discovers the run after it is persisted |
| Observer imported at 0 completed, owner progresses to 20 | observer returns the refreshed 20, not the frozen 0 |
| 10 renders with concurrency 1 | `running` is non-zero during each render; `completed` increments per render |
| Owner process dies mid-compose | stale lock reclaimed; run resumes and completes |
| Owner alive, second worker polls | no duplicate execution; poll returns live owner state |

## Remaining uncertainties

- The Hermes target run files are not available on this host, so it cannot be
  proven whether those two specific runs eventually completed or whether the
  Hermes process was restarted in a way that prevented recovery.
- The live tests ran under `next dev`. Production `next start` and serverless
  deployments were not tested. The same route/module isolation is likely, but
  unverified. In a serverless deployment, executing a run in the background
  after the start response may itself be unreliable; a durable worker or lazy
  recovery is required.
- Render and composition timings depend on resolution, scene count, host CPU,
  and FFmpeg memory. The 10-scene 1920x1080 reproduction is representative of
  the Hermes shape but not a precise timing baseline.
- The test server was terminated by the 15-minute background-terminal limit
  during the first composition attempt, not necessarily by the same mechanism
  that affected Hermes. Recovery was verified separately and succeeded.
