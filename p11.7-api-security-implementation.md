# P11.7 API Security Implementation

## 1. Chosen Identity and Authorization Design

### Constraints from recon

- Repository had no existing auth/session framework, no ownership model on `Project`, and no middleware gate.
- Existing local + MCP workflows required preserving low-friction operation.
- Requirement prohibited fake authorization via project/run IDs or client-supplied user IDs.

### Implemented minimum coherent model

- Added server-side identity extraction in [lib/security/auth.ts](lib/security/auth.ts):
  - `Authorization: Bearer <EXPLAINER_API_TOKEN>` for service callers (MCP/stdio/internal automation path).
  - Signed HTTP-only session cookie `explainer_session` for browser user flows.
- Added session bootstrap endpoint [app/api/auth/session/route.ts](app/api/auth/session/route.ts):
  - `POST` creates signed session cookie if no identity is present.
  - `GET` reports auth status.
- Added central authz and throttling layer in [lib/security/access-control.ts](lib/security/access-control.ts):
  - `requireIdentity(request)` distinguishes unauthenticated from authenticated.
  - `requireProjectAccess(request, projectId)` enforces project ownership for user sessions and allows service-token identity.
  - Unauthorized project access returns not-found semantics (404) to reduce private-resource existence disclosure.
  - `enforceThrottle(identity, bucket)` applies process-local per-identity endpoint limits.
- Added shared response mapper [lib/security/http-response.ts](lib/security/http-response.ts) for consistent 401/404/429 JSON responses and `Retry-After` for throttling.
- Added `ownerId?: string` to `Project` in [lib/types/render.ts](lib/types/render.ts).
- Extended project store in [lib/storage/project-store.ts](lib/storage/project-store.ts):
  - `createProject(input, ownerId?)` assigns ownership for user-created projects.
  - `listProjects(ownerId?)` supports owner-scoped listing.

### Local trust model

- Browser local-user path: signed cookie identity.
- MCP/service path: bearer token via `EXPLAINER_API_TOKEN` (server and MCP client env must match).
- No trust based on caller-supplied project/run IDs.
- No universal bypass via headers/query parameters.

## 4. Throttling Behavior and Limitations

### Implemented throttling

In-memory per-identity buckets in [lib/security/access-control.ts](lib/security/access-control.ts):

- `run_start`
- `run_status`
- `run_log`
- `generate_image`
- `generate_video`
- `generate_narration`
- `video_poll`
- `render_scene`
- `compose_project`

Keying model:
- Key is `throttle:<bucket>:<identity.subject>`.
- Identity subject comes from signed session user or service token principal.
- This prevents simple bypass by changing project ID/run ID while keeping same identity.

Config model:
- Env-tunable limit/window per bucket (`API_THROTTLE_*`).
- On throttle hit: 429 + `Retry-After` header.

### Limitations (explicit)

- Process-local memory only.
- Resets on process restart.
- Not shared across multiple instances.
- Not a distributed/global abuse control.

## 5. Local Access and MCP Trust Model

### Browser/local workflow

- Browser obtains session cookie through `POST /api/auth/session`.
- `ProjectWorkspace` now proactively initializes this session on mount in [components/project/project-workspace.tsx](components/project/project-workspace.tsx).

### MCP/stdio workflow

- MCP HTTP client includes bearer token when `EXPLAINER_API_TOKEN` is present in environment.
- Server accepts service identity when header matches its configured `EXPLAINER_API_TOKEN`.

### Security posture

- No bypass by query/header user ID claims.
- No trust solely from run/project IDs.
- No IP/header-based local trust assumptions added.

## 8. Remaining Deployment Checks and Known Limitations

### Remaining runtime checks (not provable from code alone)

- Verify actual network exposure/bind interfaces in runtime environment.
- Verify firewall/proxy/tunnel configuration for intended boundary.
- Verify TLS/security headers at deployment edge if exposed beyond localhost.

### Known limitations

- Project ownership is persisted in local project JSON and is first-claim for legacy ownerless projects on first authenticated access.
- Session persistence is cookie-based without external identity provider.
- Throttling is in-memory and single-process.
- This implementation does not claim LAN/public safety by itself.

## Preservation of P11.3/P11.4.1 Guarantees

Verified by unchanged run-policy/service behavior and passing production-run/rule tests:

- Provider policy enforced server-side.
- Real providers still require explicit opt-in and credentials.
- Missing credentials fail closed pre-execution.
- No silent real/mock fallback introduced.
- Existing concurrency/action/iteration limits remain in run service.
- Authz checks now occur before scheduling expensive route-triggered work.

## Deployment Status Conclusion

Conditionally ready for a verified private boundary after correct runtime secret and network configuration, while still treated as local-only pending runtime exposure verification.

Not declared safe for public exposure without additional infrastructure controls (network boundary, edge controls, distributed rate limiting, and hardened session/identity ops posture).
