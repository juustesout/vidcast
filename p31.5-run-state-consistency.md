# P31.5 — Shared Run State and Live Action Progress

Date: 2026-10-17
Scope: make production run status and logs consistent across Next.js route
instances, publish action progress while work is running, and recover
non-terminal runs on read instead of returning a false `NOT_FOUND`.
Status: implemented and verified. No commit or push.

## Verdict

The P31.4 findings were addressed at the observability/lifecycle layer rather
than by changing the scheduler:

1. Status and log routes now treat the in-memory registry as a cache. When a
   run is not present locally, or the durable copy is newer, the route loads it
   from the run store. A cold or warm route worker therefore no longer serves a
   permanent `NOT_FOUND` or a frozen snapshot.
2. A non-terminal run read by a status route is recovered lazily when no live
   execution lock exists. The existing file lock and an in-process guard prevent
   duplicate action execution.
3. The start request persists the run before returning `202`, closing the
   debounce race that produced `NOT_FOUND` immediately after start.
4. The runner publishes `running`, `completed`, and `failed` progress per
   action instead of only at iteration boundaries. Long `scene_render` and
   `final_compose` batches now update the summary while they execute.
5. A start request on a different route instance reuses an active persisted run
   for the same project instead of starting a second run.

## Root Causes Addressed

| Finding from P31.4 | Change |
| --- | --- |
| Progress only at iteration boundaries | `production-runner.ts` emits `onProgress` on action start and after each settled action |
| Registry instances are per Next.js route graph | Status/log reads load/refresh from `FileRunStore` by `runId` |
| Recovery only at service construction | `getRunForRead()` calls lazy recovery for non-terminal runs with no live lock |
| `importRun()` ignored existing runs | `refreshRun()` merges persisted state using event position and terminal status |
| Start returned before first persist | `startOrReuseRun()` awaits `flushRun(runId)` before returning |
| A second instance could start another active run | `performStart()` scans persisted active runs for the project and reuses one |

## Implementation

### Durable lookup

`lib/production/run-store.ts`

- Added optional `RunStore.findByRunId(runId)`.
- `FileRunStore` keeps a `runId -> projectId` map updated by `save()` and
  `load()`.
- `findByRunId()` first uses the map and falls back to a bounded scan of project
  run directories. A miss is removed from the map.

### Registry refresh and merge

`lib/production/run-registry.ts`

- Added `isTerminalStatus()`, `storedRunFromEntry()`, and `eventPosition()`.
- `importRun()` now reuses the same stored representation.
- Added `refreshRun()`:
  - terminal in-memory state is never downgraded to non-terminal persisted state;
  - a terminal persisted state is accepted when it is at least as recent as the
    in-memory copy;
  - non-terminal persisted state replaces the local copy only when its event
    position (`eventOffset + events.length`) is strictly greater;
  - the project-active index is updated for queued/running runs and cleared for
    terminal runs.

### Read-through and lazy recovery

`lib/production/run-service.ts`

- Added `getRunForRead(runId)` and `getRunLogForRead(runId, options)`.
- The synchronous `getRun()` remains available for owner-side internal callers
  and existing tests.
- Added `loadPersistedRun()`, `findPersistedActiveRun()`, and
  `isPersistedRunExpired()`.
- Added `ensureRunActive()`:
  - skips runs already recovered, recovering, executing, or queued;
  - respects the cross-process execution lock;
  - calls the existing `recoverRun()` when this instance may own recovery;
  - never makes a status/log read fail when recovery cannot start.
- `recoverRuns()` now uses `refreshRun()` so a second recovery refreshes an
  already imported run instead of leaving a stale snapshot.
- `executeRun()` refreshes from durable state after acquiring the lock and
  returns without executing when the run is already terminal. This protects
  against two route instances recovering the same queued run.

### Start consistency

- `performStart()` checks persisted active runs for the project before creating
  a new run, then recovers or leaves the live owner untouched.
- The new run is flushed before the start response. The existing synchronous
  same-instance start coalescing remains unchanged.

### Routes

- `app/api/production-runs/[runId]/route.ts` uses `getRunForRead()`.
- `app/api/production-runs/[runId]/log/route.ts` uses `getRunForRead()` for the
  project access check and `getRunLogForRead()` for the log page.

### Live progress

`lib/production/production-runner.ts`

- `onProgress` is emitted when an action starts (with the action in
  `runningActionIds`) and after each action settles (with updated
  `completedActionIds` or `failedActionIds`).
- The existing iteration-boundary progress emission is retained.
- No execution order, concurrency, retry, or dedupe behavior changed.

## Remaining Risks

1. **FFmpeg memory pressure is still separate.** P31.4 observed an OOM kill
   during 1920x1080 composition at roughly 7.1 GiB of 7.9 GiB RAM and a 48-byte
   orphan composition file. This report only used 1280x720 and did not change
   FFmpeg settings. OOM handling and orphan cleanup remain a follow-up.
2. **Cross-process start is not fully atomic.** Active-run reuse now consults
   durable state, and same-instance starts coalesce. Two processes starting the
   same project in the narrow window before either persists a run could still
   create two runs. Closing that fully would require a project-level start lock,
   which was outside this fix.
3. **Read-through adds filesystem work to status polls.** `findByRunId()` uses a
   cache after the first lookup, but a cold lookup may scan project directories.
   Terminal runs are still subject to the configured retention policy and will
   return `NOT_FOUND` after expiry by design.
4. **Merge uses event position.** The refresh rule prefers more events, with
   terminal status winning at equal positions. This is deterministic for the
   current append-only log, but it is a heuristic rather than a version vector.
5. **Recovery from a read is best effort.** If recovery fails before persisting
   progress, the run remains readable and a later read can retry. The read
   itself does not block on the whole production run.
