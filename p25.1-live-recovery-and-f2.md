  against the P25 fix. **PASS** (positive) plus two negative controls.

## 3. F2 — mock `generated_video` stalled after one poll

### 3.1 Live reproduction (before fix)

`project_f213d2c2-7cc7-4ba3-a2ce-7534cc1cef95` / `run_818e273d-72ca-4bf4-99ac-9b05257cdec4`
(1 `generated_video` scene, force:true, mock). Event counts:

```
video_poll_scheduled: 1
video_poll_completed: 1
run_stopped_unresolved: 1
failures: []
```

The run made exactly one poll, then stopped `unresolved` with no failures.

### 3.2 Root cause

- The fake provider (`lib/ai/video-generation/fake-provider.ts`) only reaches
  `generated` on the **third** `getStatus` call (poll 1 → `queued`, poll 2 →
  `generating`, poll 3+ → `generated`).
- The planner (`lib/production/production-planner.ts:252-266`) keeps deriving a
  `video_poll` action as `ready` for as long as the scene's generation is
  `running` and a `providerJobId` exists. It is therefore a **repeatable**
  action by design.
- The runner, however, added every successfully executed action to its
  within-batch dedup set `executedActionIds`
  (`lib/production/production-runner.ts:466-468`). On the next iteration the
  planner re-derived `video_poll` as ready, but the ready-filter
  (`production-runner.ts:387`) dropped it as "already executed". With the same
  plan signature, the loop terminated as `run_stopped_unresolved`
  (`production-runner.ts:390-413`).

### 3.3 Fix

Minimal, in the runner: on success, `video_poll` is added to
`completedActionIds` (summary/telemetry) but **not** to `executedActionIds`, so
the within-batch dedup no longer suppresses a re-derived poll while the job is
still running. It remains bounded by the run's `maxVideoPolls` /
`maxActionExecutions` / `maxIterations` limits
(`lib/production/run-service.ts:759-767`). Non-poll actions are unchanged.

### 3.4 Live verification (after fix)

`project_c424bf88-5a7b-478b-90e9-681a7c4bfdee` / `run_a6bed783-2546-4506-bf3c-06ab13bc6695`
(same shape). The polling loop now advances the job across iterations:

```
video_poll_scheduled: 3
video_poll_completed: 3
completedActionIds: [video_submit, video_poll, narration_generate]
```

`video_submit` + `video_poll` + `narration_generate` all completed: the mock
video generation reached `generated`. The previous `run_stopped_unresolved`
after one poll is gone.

### 3.5 Known mock-only limitation surfaced afterwards

With polling fixed, the run proceeded to `scene_render`, which failed with
`FFMPEG_FAILED` (HTTP 500). This is a **fake-provider asset limitation**, not a
recovery/planner defect: `FakeVideoGenerationProvider.download()` returns a
24-byte stub (`FAKE_MP4_BYTES` — an `ftyp` box only, no `moov`/`mdat`), which
FFmpeg cannot demux. Generated-image mock runs are unaffected because the fake
image asset is a valid decodable image. Making the fake video renderable was
out of scope for F2 (scope = the poll loop and job reuse); no bundled sample
video exists.

### 3.6 Job reuse / resume guarantee

Already covered and unchanged:

- `reconcileInterruptedGenerations` leaves an active video attempt **with** a
  `providerJobId` untouched and resumes it by poll
  (`lib/production/run-recovery.ts:36-65`).
- `tests/run-recovery.test.ts` — "resumes a stored video job by polling and
  does not resubmit" asserts `video_submit` is `running`/`execute:false` and
  `video_poll` is the executable action using the stored `attemptId`.
