# P32.2 — Timeline-first Background Music

Date: 2026-10-17
Scope: derive requested background-music length from the authoritative P32.1
render timeline, keep the existing loop/trim/fade composition path, and never
regenerate or overwrite an existing selection silently.
Status: implementation and verification complete. Nothing was committed or pushed.

## Verdict

1. **One timeline source.** The final video duration is the sum of
   `RenderPlanScene.duration` from `resolveRenderPlan()`. There is no second
   calculator in the music path.
2. **Music length is timeline-first.** Run generation, manual generation and the
   UI default now derive from that timeline when no explicit length is supplied.
   Explicit lengths and previously stored lengths always win.
3. **Provider bounds are respected.** The requested length is clamped to
   `3000..600000 ms`. A timeline above the maximum requests a 600 s track and the
   compositor loops it; a timeline below the minimum requests 3 s.
4. **No silent regeneration.** `prepareRunMusic` still reuses an existing usable
   selection before considering generation. `generateProjectMusic` still refuses
   to replace generated music unless `regenerate=true`.
5. **Composition is already safe for either length.** `-stream_loop -1` plus
   `atrim=0:<timeline>` loops a short track and cuts a long one; the fade-out is
   computed from the timeline and always ends at the final video frame.
6. **No new providers, dependencies, paid calls, or schema changes.**

## Implementation

### Timeline helpers (`lib/render/scene-resolver.ts`)

Already added during P32.2 recon, now used by music:

- `resolveRenderPlanDurationSeconds(plan)` = `sum(plan.scenes[].duration)`;
- `resolveProjectTimelineDurationSeconds(project)` =
  `resolveRenderPlanDurationSeconds(resolveRenderPlan(project))`.

Each scene duration is the P32.1 effective duration:

```text
authored       = scene.duration
required       = narrationDuration > authored
                 ? narrationDuration + 0.25
                 : 0
effective      = max(authored, required, 0.1)
timeline       = sum(effective)
```

`narrationDuration` is `Math.max(recorded scene narration duration, referenced
asset duration)`, the single measured-narration source.

### Requested length (`lib/render/music-mix.ts`)

New `resolveTimelineMusicLengthMs(timelineSeconds, fallbackMs = 60000)`:

```text
lengthMs = round(timelineSeconds * 1000)
lengthMs <= 0 or non-finite -> clamp(fallbackMs)
otherwise                   -> clamp(lengthMs)
clamp(x)                    -> min(600000, max(3000, round(x)))
```

Bounds mirror the ElevenLabs Music contract already present in
`music-mix.ts` and `elevenlabs-provider.ts` (`music_v2_5`, `mp3_44100_128`).

### Run path (`lib/production/run-service.ts`)

`prepareRunMusic` remains opt-in, fail-soft and runs immediately before
`final_compose`. When it reaches generation:

```text
musicLengthMs = plan.musicLengthMs
                ?? resolveTimelineMusicLengthMs(resolveProjectTimelineDurationSeconds(project))
```

The explicit run-plan value wins. An existing usable selection is still returned
before any generation request, so the timeline cannot trigger regeneration.

### Manual path (`lib/generation/music-service.ts`)

```text
requested = options.musicLengthMs ?? existing music.musicLengthMs
length    = requested === undefined
            ? resolveTimelineMusicLengthMs(timeline)
            : clamp(requested)
```

Consequences:

- explicit manual/UI/MCP length: unchanged;
- previously generated/requested length: preserved on regeneration;
- no length at all: now matches the current render timeline instead of a fixed
  60 s (60 s remains the fallback only when the project has no timeline).

### UI default (`lib/music/music-form.ts`, `background-music-panel.tsx`)

`resolveMusicDefaultDurationSeconds(project)` converts the clamped timeline
length to whole seconds. The panel uses an existing requested length first, then
the timeline default for both the input placeholder and the empty-input payload.
The helper text now says: "Leave empty to match the video timeline."

### Compositor (`lib/render/video-compositor.ts`, unchanged behaviour)

`buildMusicMixArgs` already applies:

- `-stream_loop -1` on the music input;
- `volume=<musicVolume>,atrim=0:<timeline>`;
- `afade=t=in:st=0:d=1`;
- `afade=t=out:st=<timeline - out>:d=<out>` where
  `out = min(2, max(0, timeline - in))`;
- `amix=inputs=2:duration=first:dropout_transition=0:normalize=0` and the peak
  limiter;
- `-t <timeline>` and video stream copy.

Therefore the fade-out always finishes inside the final video duration, and
short music loops while long music is trimmed.

## Residual risks

1. **Timeline above 600 s repeats the track.** Looping preserves total coverage
   but musical phrasing restarts; seamless looping is out of scope.
2. **Provider output length can differ from the request.** The compositor already
   loops/trims either way, so the video is correct even if the provider returns a
   shorter or longer file.
3. **Previously stored lengths stay sticky.** A project whose `music.musicLengthMs`
   was saved before P32.2 keeps that value on regeneration. To adopt the current
   timeline the caller must supply the new length (the UI does this when the
   field is empty only if no stored value exists). This is deliberate to avoid
   silently overwriting historical intent.
4. **No separate timeline field in the composition fingerprint.** A timeline
   change is already detected through scene render ids, narration signatures and
   output-duration validation, so adding another field would be redundant.
5. **Silence trimming is still out of scope.** The timeline uses measured
   narration duration, not speech-onset/offset detection.
6. **P32.1 remains uncommitted.** This work builds on that uncommitted timing
   change; both must be reviewed together before any commit.
