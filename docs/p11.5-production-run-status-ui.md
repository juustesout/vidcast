# P11.5 Production Run Status UI

## Summary

P11.5 adds a separate Server runner panel inside the existing Production section of the project workspace.

The existing browserrunner remains intact:
- Produce button and local batch execution are unchanged.
- Scene-level generation, render, and compose controls are unchanged.
- The new panel does not fall back to browserrunner or auto-restart failed runs.

## UI Behavior

The Server runner panel provides:
- explicit Start Server Run action
- save-before-start gating using the existing workspace save flow
- new-run versus reused-run feedback
- current run ID
- accepted provider policy snapshot
- lifecycle status for queued, running, completed, partial, failed, and unresolved
- recent retained server-run events
- restart-loss messaging when a tracked run returns NOT_FOUND
- structured API error details where available

Polling behavior:
- only runs while a server run is being tracked
- uses one managed polling cycle
- prevents overlapping requests
- ignores stale responses after invalidation or project change
- retries transient network and non-NOT_FOUND API polling failures with bounded backoff
- stops on terminal statuses and on restart-loss

Log behavior:
- the server log API paginates forward by cursor
- when attaching to a run, the panel catches up through retained pages to reach the current tail
- the panel then reveals earlier retained events locally via Load older events

## API Integration

The UI uses the existing routes only:
- POST /api/projects/[id]/production-runs
- GET /api/production-runs/[runId]
- GET /api/production-runs/[runId]/log

No server contracts were changed.

Client integration files:
- lib/client/production-run-client.ts
- lib/client/production-run-tracker.ts

Error handling preserves structured codes and details, including:
- NOT_FOUND
- PROVIDER_NOT_CONFIGURED
- POLICY_DENIED
- INVALID_ARGUMENT

## Save Gating

Server runs are never started against an unsaved draft.

The panel calls the existing saveProject flow from the workspace component and waits for a confirmed success result before sending the start request. If save fails, the run start request is not sent.

## Security Assumptions

Observed backend reality in this repository:
- the server-run routes do not enforce user/session ownership
- no middleware or route-level auth boundary was found for these endpoints
- project storage is local filesystem backed under the workspace root

UI posture:
- the panel explicitly describes the local API exposure and does not claim multi-tenant isolation
- provider-policy enforcement remains server-side
- no credentials are exposed in client-visible data

Known deployment limitation:
- if this app is exposed beyond a trusted local boundary, these routes remain unprotected by backend auth in the current codebase
- P11.5 does not invent a new auth layer because there is no existing repo convention to extend safely within this scope

## Known Limitations

- The in-memory server registry is not persistent across process restart or retention expiry; the UI surfaces this as restart-loss instead of attempting automatic recovery.
- Forward-only log pagination means the UI first catches up to the current retained tail, then reveals earlier retained events locally rather than requesting reverse pages from the server.
- No automatic run re-attachment occurs after a full page refresh.
