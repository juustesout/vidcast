# P11.1 Read-only MCP for Explainer Studio

This document describes the local read-only MCP server for Hermes.

Note: P11.3 adds separate mutating production-run tools on the same local stdio server process. The read-only tool contracts in this document remain unchanged.

## Scope

P11.1 exposes only these tools:

- `list_projects`
- `get_project`
- `get_scene`
- `get_validation_report`
- `get_production_plan`

Out of scope in this phase:

- production execution tools
- provider calls
- rendering/composition actions
- any mutation endpoints
- HTTP/SSE MCP transport

## Architecture

- Separate MCP server process in `mcp/read-only/server.ts`
- Official MCP TypeScript SDK over stdio
- Thin adapter over existing app API routes:
  - `GET /api/projects`
  - `GET /api/projects/:id`
  - `GET /api/projects/:id/validation-report`
  - `GET /api/projects/:id/production-plan`
- Existing validation and status logic is reused through:
  - `validateProject`
  - `deriveWorkflowStatus`
  - `resolveRenderPlan`
  - `deriveSceneRenderStatus`
  - `deriveCompositionReadiness`
  - `deriveCompositionArtifactStatus`

## Install and Run

1. Install dependencies:

```bash
npm install
```

2. Start the Next.js app (separate terminal):

```bash
npm run dev
```

3. Start the MCP server (stdio):

```bash
npm run mcp:readonly
```

The MCP server uses `EXPLAINER_API_BASE_URL` if set, otherwise `http://127.0.0.1:5555`.

## Hermes stdio configuration examples

Example MCP client config using npm script:

```json
{
  "mcpServers": {
    "explainer-read-only": {
      "command": "npm",
      "args": ["run", "mcp:readonly"],
      "env": {
        "EXPLAINER_API_BASE_URL": "http://127.0.0.1:5555"
      }
    }
  }
}
```

Example with direct tsx command:

```json
{
  "mcpServers": {
    "explainer-read-only": {
      "command": "npx",
      "args": ["tsx", "mcp/read-only/server.ts"],
      "env": {
        "EXPLAINER_API_BASE_URL": "http://127.0.0.1:5555"
      }
    }
  }
}
```

## Tool contracts

### `list_projects`

- Arguments: `{}`
- Returns: stable project summaries (`id`, title, counts, duration target, updatedAt)
- Error cases:
  - `API_UNAVAILABLE`
  - `API_ERROR`

### `get_project`

- Arguments: `{ "projectId": "..." }`
- Returns: full project object
- Error cases:
  - `INVALID_ARGUMENT`
  - `NOT_FOUND`
  - `API_UNAVAILABLE`
  - `API_ERROR`

### `get_scene`

- Arguments: `{ "projectId": "...", "sceneId": "..." }`
- Returns: scene object with owning `projectId`
- Error cases:
  - `INVALID_ARGUMENT`
  - `NOT_FOUND` (project or scene)
  - `API_UNAVAILABLE`
  - `API_ERROR`

### `get_validation_report`

- Arguments: `{ "projectId": "..." }`
- Returns: structured report with validation, workflow, render readiness, scene status, composition state and blockers
- Error cases:
  - `INVALID_ARGUMENT`
  - `NOT_FOUND`
  - `API_UNAVAILABLE`
  - `API_ERROR`

### `get_production_plan`

- Arguments: `{ "projectId": "..." }`
- Returns: structured production plan for one project
  - `projectId`
  - `generatedAt`
  - `plan.actions` (existing planner action IDs, statuses, dependencies and payloads)
  - `plan.summary` (ready, running, current, failed, waiting, blocked, skipped)
  - `groupedByScene`
  - `derivedFlags` (`hasBlockingActions`, `hasWaitingDependencies`, `readyActionCount`)
- Error cases:
  - `INVALID_ARGUMENT`
  - `NOT_FOUND`
  - `API_UNAVAILABLE`
  - `API_ERROR`

## Read-only guarantees

- MCP tools call only `GET` endpoints.
- No filesystem mutation, delete actions, or shell execution in MCP tools.
- No generation, render, composition, or provider calls are triggered by MCP tools.
- No API keys or secrets are returned in tool payloads.
- Reading a production plan inspects planner state only; it does not execute production actions.

Seed behavior note:

- Existing `projectStore.listProjects()` and `projectStore.getProject()` can trigger initial seed project creation when the projects directory is empty.
- This is existing storage behavior outside planner logic and is unchanged by the production plan endpoint/tool.

## Mock-first policy for next phases

P11.1 is inspect-only. Future mutating phases should default to fake/mock execution and require explicit opt-in before any real provider call is allowed.
