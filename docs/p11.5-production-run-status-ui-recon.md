# P11.5 Production Run Status UI Recon

## 1) Current Workspace and Browserrunner Architecture

Primary workspace UI is centered in components/project/project-workspace.tsx.

Current production UX is browserrunner-first:
- runProduceReady executes client-side orchestration via runProductionBatch.
- executeProductionAction performs per-action browser API calls for image/video submit+poll, narration, render, compose.
- In-memory client run state is tracked in local React state: batchOutcome, batchSummary, batchEvents, batchFailedActionIds.
- Production log modal shows only local batchEvents for this tab session.

Existing polling behavior today:
- Video polling only, tied to active generated_video attempts.
- Uses setInterval(5000) with overlap guard via isVideoPollingRef.
- Poll loop ends when no active video attempt IDs remain.

Save/unsaved behavior today:
- saveProject is explicit and called before major operations (produce/render/compose).
- updateProject mutates draft and resets save message.
- No explicit dirty-state guard, no beforeunload prompt, no route-leave confirmation.

What clearly belongs to browserrunner and should remain:
- runProduceReady and executeProductionAction in project-workspace.tsx.
- Fine-grained scene-level manual controls and immediate local orchestration feedback.
- Existing generation polling for browser-submitted video jobs.

What can safely add headless-run visibility without replacement:
- A separate server-run status panel in the existing Production section.
- Start/reuse button for server run using existing run APIs.
- Status/log polling and pagination isolated from browserrunner state.

## 2) Server-Run API Contract and Semantics

### Start/Reuse Run
Route: app/api/projects/[id]/production-runs/route.ts
Method: POST
Input schema:
- mode: mock | real (optional)
- providers (optional):
  - image: fake | openai
  - video: local | openai
  - narration: fake | elevenlabs
- maxIterations: positive int <= 10000 (optional)
- limits (optional per action): positive int <= 128

Success response:
- status 202 when new queued run created
- status 200 when active run reused
- payload: { run, reused }

Error response:
- status 400, code INVALID_ARGUMENT on zod payload issues
- otherwise RunServiceError passthrough: { message, code, details }

Duplicate start semantics:
- If project already has active queued/running run, no new run is created.
- Existing run is returned with reused=true and HTTP 200.

### Run Status
Route: app/api/production-runs/[runId]/route.ts
Method: GET
Success:
- status 200, payload { run }

Unknown/lost run:
- status 404, code NOT_FOUND
- message indicates run may be expired from memory or lost after process restart.

### Run Log Page
Route: app/api/production-runs/[runId]/log/route.ts
Method: GET
Query:
- cursor: int >= 0 optional
- limit: int > 0 optional

Validation errors:
- status 400, code INVALID_ARGUMENT for invalid cursor/limit

Success:
- status 200, payload { log }
- log fields:
  - runId
  - cursor
  - nextCursor
  - hasMore
  - items: [{ cursor, event }]

Pagination semantics from run-registry:
- Cursor is absolute event cursor.
- Registry may trim old events via ring buffer; when cursor is older than retained offset, page starts at earliest retained cursor.
- nextCursor points to the next unread cursor after returned items.
- hasMore indicates additional retained items after nextCursor.

### Lifecycle and Status Model
From run-types and run-service:
- Headless run statuses: queued, running, completed, partial, failed, unresolved.
- acceptedConfig snapshot is locked at start:
  - policy snapshot (mode, allowRealProviders, exact providers)
  - execution limits
- Status transitions:
  - queued -> running -> terminal (completed/partial/failed/unresolved)

### Error/Policy Semantics
From run-policy and run-service:
- Server enforces policy before queueing actions.
- mock mode strictly allows fake/local providers only.
- real mode requires allowRealProviders=true and explicit real providers.
- real mode preflight enforces required credentials based on actionable plan:
  - OPENAI_API_KEY for real visual actions
  - ELEVENLABS_API_KEY for real narration actions
- Missing required credentials reject pre-execution with PROVIDER_NOT_CONFIGURED (409).

### Authentication/Authorization Behavior
Observed in these routes:
- No explicit auth/session/ownership checks in app/api/projects/[id]/production-runs/route.ts, app/api/production-runs/[runId]/route.ts, app/api/production-runs/[runId]/log/route.ts.
- Current workspace appears local-first; access control boundaries are not implemented at these endpoints.

## 3) Recommended UI Integration Point

Smallest coherent location:
- Extend the existing Production section in components/project/project-workspace.tsx (where local production status/log already lives).

Why this point:
- Users already run production there.
- Existing copy/layout/status language can be reused.
- Avoids introducing a new navigation surface.

Recommended placement:
- Add a compact Server Run panel beside or directly below current Produce controls.
- Keep browserrunner panel unchanged and visibly separate.
- Label explicitly:
  - Browser runner (existing)
  - Server runner (headless)

## 4) Minimal Component and State Model

Proposed first-version state (client only):
- serverRunMode: idle | starting | tracking | error
- activeRunId: string | null
- serverRunSnapshot: latest run payload or null
- serverRunError: displayable API error
- logItems: appended/merged run log entries
- logCursorNext: nextCursor
- logHasMore: boolean
- pollingInFlightRef: boolean
- pollTimerRef + requestTokenRef for stale-response guard

Essential first-version behaviors:
- Start or reuse a run via POST /api/projects/[id]/production-runs.
- Surface reused flag and runId.
- Poll GET /api/production-runs/[runId] while queued/running.
- Poll GET /api/production-runs/[runId]/log with cursor-based incremental fetch.
- Stop polling on terminal status.
- Show terminal outcomes: completed, partial, failed, unresolved.
- Provide Load older events action using cursor pages.
- On 404 NOT_FOUND for known runId: show restart-loss/expiry message and stop polling.

Optional enhancements (defer):
- Persist last runId per project in URL/local storage.
- Auto-expand diagnostics by action type.
- Rich timeline grouping and filtering.

## 5) Polling, Cancellation, Cleanup, Restart-Loss Handling

Recommended polling policy:
- Poll only when activeRunId exists and status is queued/running.
- Poll status every 2-3s while active; stop immediately on terminal.
- Poll log incrementally with cursor since last nextCursor.

Required safety mechanics:
- No overlapping requests: skip tick if request in flight.
- Stale response protection: monotonic request token; ignore older responses.
- Cleanup on unmount or project change: clear timer and invalidate token.
- Network errors: keep state as tracking, surface transient warning, retry next tick with backoff cap (for example 2s -> 4s -> 8s, max 15s) without flipping run to failed.
- 404 NOT_FOUND while tracking: treat as restart-loss/expiry signal, stop polling, show non-terminal diagnostic state to user.

Resource behavior:
- No polling when idle.
- No background workers/websockets/new infra.
- Reuse existing fetch patterns and lightweight client helpers.

## 6) Authentication and Provider-Policy Considerations

Must preserve:
- Provider policy is server-authoritative and immutable per run acceptedConfig.
- UI only sends optional mode/providers; never interprets or bypasses policy.
- No credentials exposed in UI; only display server-safe message/code/details.
- No silent fallback to browserrunner after headless run error.
- No auto-restart for failed/unresolved runs.
- Duplicate starts handled as contract says (reused=true).

UX clarity recommendation:
- Distinct labels for execution mode/source.
- Display acceptedConfig.policy from run snapshot so users can see actual locked mode/providers.

## 7) Tests to Add and Regression Risks

Current testing conventions:
- Vitest in node environment.
- Mostly pure logic/service tests.
- Limited React output testing via react-dom/server static markup.
- Existing MCP stdio integration tests can be used as contract confidence but are not UI tests.

Recommended tests for P11.5 scope:
1. Client API helper tests for server-run endpoints (success, duplicate start, 400, 404, 409).
2. Polling controller/state-machine tests as pure functions:
- idle -> queued/running -> terminal
- stop polling on terminal
- no overlap
- stale response dropped
- network transient retry behavior
- 404 restart-loss handling
3. Log pagination tests:
- append new page by nextCursor
- load older pages
- ring-buffer cursor jump handling
4. Integration-style component tests (minimal) for panel rendering states using mocked fetch and controlled timers.
5. Regression guard that browserrunner controls still render and runProduceReady path remains intact.

Regression risks to watch:
- Interleaving server-run polling state with existing video polling side effect.
- UI confusion between browser and server run statuses.
- Starting run against stale unsaved draft (must keep explicit save-before-start rule if chosen).

## 8) Concise Implementation Plan (<= 8 tasks)

1. Add lightweight client helper module for production-runs APIs (start/get status/get log) using existing fetch style.
2. Add Server Run panel component near current Production controls in project-workspace.tsx.
3. Implement start/reuse action with clear reused/new feedback and stored activeRunId.
4. Implement guarded polling loop for run status + incremental log fetch while active.
5. Implement terminal-state rendering and explicit restart-loss handling for NOT_FOUND.
6. Implement log pagination controls using cursor and hasMore semantics.
7. Add tests for helper contracts and polling state transitions; add minimal UI render-state test.
8. Run regression suite ensuring browserrunner behavior remains unchanged.

Expected files to change (recon recommendation):
- components/project/project-workspace.tsx
- components/project/production-workflow.tsx (only if minor shared status display hook-in is needed)
- lib/client/production-run-client.ts (new)
- tests for helper/polling/component state:
  - tests/production-run-client.test.ts (new)
  - tests/production-run-status-polling.test.ts (new)
  - tests/project-workspace-server-run-panel.test.tsx (new, minimal)

Potential blockers:
- Current node test environment may limit rich client interaction tests; prefer pure polling state tests plus minimal static render assertions unless test env changes are approved.
- No built-in auth boundaries in current APIs; UI should not imply multi-tenant protection that server does not enforce.

## Smallest Safe Implementation Scope Recommendation

Implement only a compact server-run panel inside the existing Production area of project-workspace.tsx, with start/reuse, active polling, terminal status display, and cursor log paging.

Do not replace browserrunner controls, do not alter API contracts, and do not add persistence or background infrastructure in this phase.
