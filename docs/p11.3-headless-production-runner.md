# P11.3 Headless Production Runner

This phase adds server-side production execution so Hermes can start, follow, and diagnose runs without a browser session.

## Scope

Included:

- Headless orchestration in:
  - `lib/production/run-service.ts`
  - `lib/production/run-registry.ts`
  - `lib/production/run-policy.ts`
- API endpoints:
  - `POST /api/projects/:id/production-runs`
  - `GET /api/production-runs/:runId`
  - `GET /api/production-runs/:runId/log?cursor=&limit=`
- MCP mutating tools:
  - `run_production`
  - `get_run_status`
  - `get_run_log`
- Shared stdio transport with existing P11.1/P11.2 read-only tools.

Out of scope:

- persistent run storage
- distributed workers or remote queues
- cancel/pause/resume
- remote MCP transport
- changes to read-only tool contracts

## Architecture

- Reuses `runProductionBatch` and `deriveProductionPlan`.
- Reuses existing action services:
  - image generation
  - video submit/poll
  - narration generation
  - scene render
  - final compose
- Keeps UI routes/components intact. Browser runner remains unchanged.

## Provider Policy (Fail-Closed)

Policy is resolved and validated on the server before a run is accepted.

Default mode is `mock`.

- `mock` mode providers are locked to:
  - image: `fake`
  - video: `local` (fake adapter)
  - narration: `fake`
- `real` mode requires explicit server opt-in and uses real providers.

Key guarantees:

- Provider choice is fixed at run start and stored in run metadata.
- Explicit run policy cannot bypass server policy.
- Missing required credentials fail preflight; run does not start.
- No silent fallback from explicit real to fake/local or reverse.

## Server Configuration

- `EXPLAINER_API_BASE_URL`: MCP API base URL (defaults to `http://127.0.0.1:5555`)
- `PRODUCTION_RUN_ALLOW_REAL_PROVIDERS`: `true|false` (default `false`)
- `PRODUCTION_RUN_DEFAULT_MODE`: `mock|real` (default `mock`, forced to `mock` when real providers are disabled)
- `PRODUCTION_RUN_MAX_ACTIVE`: global concurrent runs across projects
- `PRODUCTION_RUN_MAX_ITERATIONS`: batch iteration cap
- `PRODUCTION_RUN_MAX_ACTIONS`: total action execution cap per run
- `PRODUCTION_RUN_MAX_VIDEO_POLLS`: video poll cap per run
- `PRODUCTION_RUN_MAX_EVENTS`: in-memory log ring size per run
- `PRODUCTION_RUN_RETENTION_MS`: finished run retention window
- `PRODUCTION_RUN_MAX_LOG_PAGE_LIMIT`: hard cap for log page size
- Optional per-action concurrency limits:
  - `PRODUCTION_RUN_CONCURRENCY_IMAGE`
  - `PRODUCTION_RUN_CONCURRENCY_VIDEO_SUBMIT`
  - `PRODUCTION_RUN_CONCURRENCY_VIDEO_POLL`
  - `PRODUCTION_RUN_CONCURRENCY_NARRATION`
  - `PRODUCTION_RUN_CONCURRENCY_RENDER`
  - `PRODUCTION_RUN_CONCURRENCY_COMPOSE`

## Lifecycle and Concurrency

Lifecycle:

- `queued -> running -> completed | partial | failed | unresolved`

Rules:

- At most one active run per project.
- Duplicate starts return the existing active run.
- Runs for different projects are globally bounded by `PRODUCTION_RUN_MAX_ACTIVE`.

## Logging

- Events are append-only while a run is active.
- Logs are paginated with `cursor` and `limit`.
- Event payloads are sanitized; secrets and auth tokens are not exported.
- Unknown run IDs return a stable not-found message including restart-loss context.

## Restart Behavior

Run registry is in-memory only.

- Process restart drops run status/history.
- Status/log lookups for unknown run IDs return `NOT_FOUND` with a hint that run state may have been lost after restart.

## MCP Integration

Both tool groups run over the same local stdio server process:

- read-only tools from P11.1/P11.2
- mutating production run tools from P11.3

Start command remains local stdio:

```bash
npm run mcp:local
```

Compatibility alias:

```bash
npm run mcp:readonly
```
