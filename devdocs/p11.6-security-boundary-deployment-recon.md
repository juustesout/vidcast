## 3. Existing Authentication and Authorization Mechanisms

## 3.1 What exists (verified)

- Input validation exists in multiple routes via zod/manual checks.
- Path traversal safety checks exist in file-serving and media store path resolvers.
- Concurrency/resource guardrails exist for headless runs and some action services.

## 3.2 What does not exist (verified in repository)

- No user identity/session model in project types.
  Evidence: Project type has no owner/user fields in [lib/types/render.ts](lib/types/render.ts).
- No route middleware-based auth gate.
  Evidence: no middleware.ts in workspace.
- No per-route auth/session checks for production routes and related mutation routes.
- No project ownership authorization helper usage in inspected routes/services.
- No CSRF protection layer found (token/origin enforcement) in app API routes.
- No explicit rate limiting by client identity/IP in routes.

## 3.3 Implication

Current app behavior is effectively capability-by-network-access and identifier knowledge, not identity/ownership authorization. Run IDs and project IDs are identifiers, not authorization grants.

## 4. Threat Assessment (Likelihood, Impact, Evidence, Unknowns)

Scale used:
- Likelihood: Low / Medium / High
- Impact: Low / Medium / High

### Scenario A: Unauthenticated caller starts a real-provider production run

- Likelihood:
  - High if endpoint is network-reachable.
  - Low if strictly loopback-only and host access is trusted.
- Impact: High (provider spend + compute usage).
- Evidence:
  - No auth check in [app/api/projects/[id]/production-runs/route.ts](app/api/projects/%5Bid%5D/production-runs/route.ts).
  - Start path enqueues execution in startOrReuseRun() [lib/production/run-service.ts](lib/production/run-service.ts).
  - Real-mode gate exists (policy/credentials), but it is not an identity check.
- Unknowns:
  - Actual deployment exposure (loopback vs LAN/public).

### Scenario B: Unauthorized caller reads another project run status/logs

- Likelihood:
  - High if runId/projectId known and endpoint reachable.
- Impact: Medium to High (operational metadata + diagnostic leakage).
- Evidence:
  - No ownership checks in run status/log routes.
  - getRun/getRunLog use runId lookup only [lib/production/run-service.ts](lib/production/run-service.ts).
- Unknowns:
  - Practical discoverability of IDs in specific deployment.

### Scenario C: Caller guesses or obtains run ID

- Likelihood: Medium (UUID guessing is hard, but IDs can leak via logs/UI/network capture/shared terminals).
- Impact: Medium (status/log disclosure), potentially higher if correlated with project info.
- Evidence:
  - runId is UUID-based createId() [lib/utils/ids.ts](lib/utils/ids.ts).
  - No secondary authorization check at run lookup endpoints.

### Scenario D: Repeated requests consume provider credits/CPU/memory/rendering capacity

- Likelihood: High if reachable.
- Impact: High.
- Evidence:
  - Mutating endpoints trigger provider calls/ffmpeg/work writes.
  - Service-level locks and run limits exist but no caller-level throttling.
  - run-service limits in [lib/production/run-service.ts](lib/production/run-service.ts), generation locks in [lib/generation/image-generation-service.ts](lib/generation/image-generation-service.ts), [lib/generation/video-generation-service.ts](lib/generation/video-generation-service.ts), [lib/generation/narration-service.ts](lib/generation/narration-service.ts), composition lock in [lib/render/video-composition-service.ts](lib/render/video-composition-service.ts).

### Scenario E: Browser from another origin triggers state-changing request

- Likelihood: Medium.
- Impact: Medium to High (if endpoint reachable and request shape permitted).
- Evidence:
  - No explicit CSRF/origin checks in routes.
  - Some endpoints use JSON body (harder for basic cross-site form submission), others accept multipart form data and could be CSRF-relevant if/when cookie auth is introduced.
- Unknowns:
  - Future auth mode (cookie/session) and browser deployment context.

### Scenario F: Public reverse proxy or tunnel exposes routes intended for local use

- Likelihood: Unknown (runtime/infrastructure dependent).
- Impact: High.
- Evidence:
  - Repository has no enforceable app-level auth boundary that would protect if exposed.
  - local-first docs are intent, not transport enforcement.
- Unknowns:
  - Whether external exposure currently exists.

### Scenario G: Error responses/logs reveal sensitive internals

- Likelihood: Medium.
- Impact: Medium.
- Evidence:
  - Render/composition errors can include detailed diagnostics; run logs preserve sanitized messages but redact only token-like patterns.
  - Sanitization logic in [lib/production/run-registry.ts](lib/production/run-registry.ts).
  - renderer error details in [lib/render/renderer.ts](lib/render/renderer.ts).
- Unknowns:
  - Exact details emitted by provider/ffmpeg errors in production incidents.

## 5. Provider-Policy and Resource-Protection Review (P11.3/P11.4.1 Guarantees)

## 5.1 Verified guarantees preserved

- Policy locked at run acceptance and stored in acceptedConfig.
  - resolveRunConfig()/createRun() in [lib/production/run-service.ts](lib/production/run-service.ts).
- Real-provider opt-in and credential preflight enforced server-side before scheduling work.
  - resolveRunPolicy()/assertRunPolicyPreflight() in [lib/production/run-policy.ts](lib/production/run-policy.ts).
- Missing required credentials fail closed with PROVIDER_NOT_CONFIGURED semantics.
  - mapping in startOrReuseRun() [lib/production/run-service.ts](lib/production/run-service.ts).
- No implicit fallback between real and mock/local in policy resolver logic.
  - provider constraints in [lib/production/run-policy.ts](lib/production/run-policy.ts).
- Concurrency and action limits enforced for headless runs.
  - runner/queue limits in [lib/production/run-service.ts](lib/production/run-service.ts).
- Duplicate active run reuse per project enforced.
  - getActiveRunByProject() and reuse in [lib/production/run-registry.ts](lib/production/run-registry.ts), [lib/production/run-service.ts](lib/production/run-service.ts).

## 5.2 Critical boundary gap

- Run IDs are not treated as sole authorization mechanism intentionally, but currently functionally they are sufficient for access because no identity/ownership checks exist on run status/log endpoints.
- Authz failures do not currently occur before protected data return because authz layer is absent.

## 6. Deployment Profile Recommendations

## Profile A: Single-user workstation, loopback-bound only

Required controls:
- Verify process bind address is loopback-only.
- Keep OS account trusted and locked.
- Do not expose port forwarding/tunnels.
- Keep provider keys only in local environment and avoid shell history leakage.

Assessment for current codebase:
- Conditionally acceptable if loopback-only is verified and host trust assumptions hold.

## Profile B: Trusted LAN or private VPN

Required controls before use:
- Add application authentication and project-level authorization.
- Restrict network access by firewall/VPN ACL to intended operators.
- Add request throttling/rate limits for mutating routes.
- Define explicit origin/CSRF policy if cookie/session auth is used.

Assessment for current codebase:
- Not ready without additional boundary controls.

## Profile C: Public internet or public tunnel

Required controls before use:
- Strong authN + authZ in app layer.
- Reverse-proxy/WAF rate limiting and abuse controls.
- TLS/security headers at edge.
- CSRF/origin controls for browser auth flows.
- Security review of error payloads and log data minimization.

Assessment for current codebase:
- Not ready for exposure beyond trusted local environment.

## 7. Minimal Remediation Plan (max 8 tasks)

### Must-fix before any non-local exposure

1. Add a reusable server-side auth gate and project authorization helper, then enforce it in production-run routes and related mutating routes.
2. Introduce project ownership linkage in persistent model and enforce owner checks on project and run data reads/writes.
3. Add run-to-owner authorization checks for GET /api/production-runs/[runId] and GET /api/production-runs/[runId]/log.
4. Add request throttling for expensive mutating endpoints (production-runs start, generation submit/poll, render, compose), with sensible per-client and global ceilings.
5. Tighten error response policy for externally exposed profiles (preserve operability, reduce path/internal diagnostic leakage in unauthenticated/unauthorized contexts).

### Conditional hardening by deployment profile

6. If cookie/session auth is used, add CSRF/origin protections for state-changing browser routes and validate same-site assumptions.
7. If any LAN/public exposure exists, enforce infrastructure controls: bind/interface restrictions, firewall/proxy ACLs, TLS edge policy, and tunnel prohibition/allowlist.

### Optional future improvements

8. Add persistent run registry with explicit access policy and audit logging for run start/status/log access decisions.

## 9. Runtime Checks Still Required and Safe Procedure

These checks were not provable from repository alone and must be validated in the running environment.

1. Verify bind address and listening interface for Next process.
   - Safe check example: inspect active listeners for configured app port and bound address using OS tools.
2. Verify firewall and network ACL exposure.
   - Safe check example: from a second host in same network segment, test TCP reachability to app port without invoking mutating endpoints.
3. Verify reverse proxy/tunnel status.
   - Safe check example: inspect running services/process manager and edge config for explicit publish rules.
4. Verify HTTPS/TLS/security headers at deployed edge, if any.
   - Safe check example: read-only curl/head request to health endpoint and inspect headers.
5. Verify that no provider-spend routes are externally reachable unintentionally.
   - Safe check example: read-only probe GET /api/health and GET /api/projects (no mutating probes).

Safety constraints for runtime validation:
- Do not invoke real-provider generation endpoints.
- Do not run destructive load tests.
- Do not print secret values.

## Final Recommendation

Status: not ready for exposure beyond a trusted local environment.

- Safe for local-only use only when loopback-only binding and host trust are verified at runtime.
- Conditionally safe behind a verified private boundary only after adding app-layer authN/authZ and endpoint throttling.
- Not ready for LAN/public exposure in current repository state due to absence of enforced identity/ownership authorization on production and project APIs.
