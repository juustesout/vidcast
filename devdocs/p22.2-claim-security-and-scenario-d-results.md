## 2. Review findings (no code changed)

### 2.1 Token storage - PASS

- Raw token = 32 random bytes, base64url (~43 chars, 256-bit entropy).
- Only `sha256(token)` is persisted, in a sibling `claim.json`
  (`getProjectClaimPath` = `projects/<id>/claim.json`).
- Verified on disk: `claim.json` contains a `tokenHash` and **no** raw token;
  `project.json` does **not** contain the token (evidence step 2).
- The generic file route only serves `assets|references|renders|previews`
  (`resolveSafePath`), so `claim.json` and `project.json` are not web-served.
- Recommendation (not a flaw): `claim.json` is created with default file perms
  (0644). In a shared-host, multi-user filesystem that is world-readable; in the
  single-tenant container it is fine.

### 2.2 Responses - PASS

- Claim success returns `{ project }` only (no token, no hash).
- `GET /api/projects/<id>` (owner) and the `/projects/<id>` page contain neither
  the token nor `claimToken`/`tokenHash` (evidence step 6).
- `POST /api/projects` returns `claimToken` **only** for service callers; a user
  creation returns no token and assigns ownership directly (verified).

### 2.3 Logs - PASS

- No `console.*` logs a token, hash, request body or `Authorization` header in
  `lib/`, `app/`, `mcp/`. The only logging is warn-on-unreadable-project and an
  MCP startup error.
- Next.js dev log for the whole run shows method + path + status only; a grep
  for `claimToken|tokenHash|Authorization|explainer_session` found nothing.

### 2.4 Expiry - PASS

- Default TTL 7 days, overridable via `EXPLAINER_CLAIM_TOKEN_TTL_MS`.
- `isClaimExpired` treats a missing value as not-expired, a malformed value as
  **expired** (fail-closed), and a past timestamp as expired.
- `redeemClaim` deletes the record and returns `invalid` for an expired token.
- Note (policy, not a flaw): after a token expires, `hasPendingClaim` is false,
  so the project reverts to the legacy id-based first-claim behavior and remains
  claimable by id. The capability window is bounded, and the stale `claim.json`
  is cleaned on the next `redeemClaim`; the legacy gate does not clean it.
  Consider treating an expired claim as "keep the project unclaimable" if that
  is the desired end state.

### 2.5 Consumption / single-use - PASS (in-process)

- On success the owner is written and `claim.json` is deleted (verified:
  `claimFileRemoved: true`).
- Replay with the same token after success -> `409 claim.alreadyClaimed`; the
  owner is unchanged (evidence step 7).
- Ordering in `redeemClaim` is: missing project -> `not_found`; owned ->
  `already_owned`; then token match. So a wrong token against an already-owned
  project returns `409` (ownership checked first), not `403`. This is correct
  fail-closed behavior and also avoids a token oracle on owned projects.
- `claimTokenMatches` uses `timingSafeEqual` on equal-length fixed-length
  digests; unsalted SHA-256 is fine for a 256-bit random token.

### 2.6 Access control and the three ownership paths - PASS

- Claim endpoint requires identity, rejects `service` (`403`), and binds
  ownership to the signed-cookie `user` subject only.
- The three id-based first-claim paths now skip pending-claim projects:
  - `requireProjectAccess` legacy branch (`lib/security/access-control.ts:92`);
  - `getProjectForIdentity` page branch (`lib/security/page-access.ts:37`);
  - `claimUnownedProjects` bulk claim (`lib/storage/project-store.ts:808`).
- Verified live: a brand-new session (`POST /api/auth/session`, which calls
  `claimUnownedProjects`) did **not** steal the claimable project
  (`ownerId` stayed empty; evidence step 4).
- P22's `applyProjectUpdate` still forces `ownerId: existingProject.ownerId`, so
  a patch cannot reassign or clear ownership.
- `already_owned` (`409`) does disclose, to any authenticated caller, that a
  given project id is owned. Ids are unguessable UUIDs and the caller must be
  authenticated; acceptable, noted for completeness.

### 2.7 MCP token delivery - PASS with a documented exposure surface

- `create_project` returns `claimToken` in `structuredContent.data` **and** in
  the `content[0].text` JSON (`asToolResponse`). So the token appears in the MCP
  tool result, which is exactly the intended out-of-band channel.
- Exposure surface (inherent to out-of-band delivery, outside this repo): the
  token is visible to the MCP client/agent and is typically persisted in the
  agent's tool-result log / conversation transcript. The tool description warns
  not to place it in a URL, log or analytics event. No server-side logging,
  responses, or error messages expose it.
- The token is duplicated in both `structuredContent` and the text block
  (minor; two copies in one result).

### 2.8 Verdict

**No critical security flaw.** The capability model holds: only the holder of the
server-minted, single-use token, presenting it from an authenticated browser
session, can take ownership of a service-created project. Continue to Scenario D.

## 3. Atomicity scope (item 2): single-process only

- `withKeyedLock` (`lib/utils/keyed-mutex.ts`) is an **in-process** `Map`-based
  async mutex. It serializes callers sharing one JS module instance; there is no
  file or OS lock.
- Consequently, `redeemClaim` is atomic **only within a single Node process**.
  File writes themselves are safe across processes (`project.json` is written
  temp-then-rename), so there is no corruption - but the read-check-write of
  ownership is not serialized across processes.
- Multi-process risk: if two processes (e.g. `PM2` cluster mode, multiple
  containers/instances sharing the `projects/` volume, or any future horizontal
  scale-out) redeem the **same** token concurrently, both can read the project
  as ownerless, both can match the token, and both can write `ownerId`. Then:
  - both callers may receive `200 claimed`;
  - the final owner is the last writer (nondeterministic);
  - `claim.json` is deleted twice (idempotent).
  This weakens the "exactly one owner" guarantee; it does **not** let an
  attacker without the token in, because the token is still required.
- Local test environment: **not affected.** `next dev` and `next start` run a
  single Node process, and Vitest runs one worker per test file, so the
  in-process lock is sufficient here. The Scenario D run above was single-process
  and behaved correctly.
- Recommendation if scaling out: back `projectLockKey` with a cross-process lock
  (lockfile with `O_EXCL`/`flock`) or move ownership to a transactional store,
  and/or make the claim write a conditional/compare-and-set on `ownerId` being
  empty.

## 7. Separate functional bug found (not security): image-scene runs stall `unresolved`

Not a claim issue. Reproduced deterministically.

**Symptom.** A production run for a project containing a `generated_image` scene
ends `unresolved` with `final_compose` stuck `waiting_dependency`, so no MP4 is
produced. A structurally identical `blank` scene completes.

**Minimal repro (MCP, mock, no browser):**

1. `create_project` (any title).
2. `update_project` with exactly one scene:
   `{ id:"scene-1", order:1, duration:4, type:"image", narration:{text:"...",status:"planned"}, visual:{kind:"generated_image",generation:{kind:"image",status:"planned",prompt:"A calm blue gradient background"}}, render:{motion:{preset:"zoom_in"},transition:{type:"fade"}}, overlay:{type:"none"}, referenceIds:[] }`
3. `run_production { projectId, mode:"mock", force:true, maxIterations:24, limits:{ image_generate:1, narration_generate:1, scene_render:1, final_compose:1 } }`
4. Poll `get_run_status`.

**Observed (image-only):** terminal `unresolved`, summary `{completed:3, waiting:1}`,
`failedActionIds:[]`, `get_project_compositions.available:false`. The final plan
lists `scene:scene-1:scene_render` as `ready` (execute:true) **even though it is
already in `completedActionIds`**, and `project:final_compose` waits on it; the
runner then stops with `run_stopped_unresolved`. In one run the completed
`narration_generate` also re-surfaced as `running`, and the refresh/replan did
not mark completed outputs `current`.

**Observed (blank-only, same shape but `kind:"blank"`):** `completed`,
summary `{completed:3}`, composition `available:true`. So the trigger is the
`generated_image` scene path.

**Likely root-cause area:** after `image_generate` and `scene_render` complete,
the refresh + replan in `lib/production/production-planner.ts` does not mark the
image scene's render output as current (`deriveSceneRenderStatus` returns
not-`rendered` -> `ready` at line ~333, while `compositionReadiness` still lists
the scene in `needsSceneRenderIds` -> `waiting_dependency` at line ~431). The
runner will not re-execute an action id that is already in `completedActionIds`,
so the ready render and its dependent compose deadlock and the run stops as
`unresolved`.

**Impact.** The hermes_test_002 Scenario A/D happy path (image + blank scene)
cannot reach `completed` on this build; only fully blank/output-free projects
compose. This is independent of P22.1.

**Proposed fix (separate task, not applied):** align the scene-render
"current/rendered" determination in `deriveSceneRenderStatus` with the
`compositionReadiness` view so a just-rendered image scene is reported `current`
(and thus not re-blocking `final_compose`); and/or make the runner treat a
"ready" action whose id is already completed as satisfied instead of stopping
`unresolved`. Add a regression test: one `generated_image` scene + `run_production`
mock -> `completed` with a composition artifact.
