# P29.2 Text Overlay Authoring Recon

Recon only. No code changes, no commits, no paid API calls. Every claim below is
verified against the current working tree at HEAD `0e25d09`
(`feat(render): add per-scene text overlays`). Section 7 is a recommendation;
nothing here is implemented yet.

P29.1 shipped the renderer half of per-scene text overlays (FFmpeg `drawtext`
with `textfile=`, plus optional `style`/`timing`). P29.2 asks a narrower
question: **can the existing project / scene authoring workflow actually author,
validate, save, and re-render those `style`/`timing` fields end to end —
especially through MCP `update_project` — without any code changes?**

Answer: yes for the data path (fields are carried through and drive the render
fingerprint), but there are real gaps in **validation** and in the **UI**. The
feature is currently only reachable through the REST/MCP API, not the editor.

## 1) Scope and Method

Inspected, read-only:
- MCP authoring surface: `mcp/authoring/tools.ts`, `mcp/authoring/api-client.ts`
- REST update path: `app/api/projects/[id]/route.ts` -> `lib/projects/project-update.ts`
- Shape guard: `lib/projects/project-patch-shape.ts`
- Normalization: `lib/projects/normalize-project.ts`
- Runtime validation: `lib/validation/project-validation.ts`, `lib/constants.ts`
- Render planning/status: `lib/render/scene-resolver.ts`,
  `lib/render/render-fingerprint.ts`, `lib/render/render-status.ts`,
  `lib/production/production-planner.ts`
- Production/render/download routes under `app/api/`
- UI: `components/project/project-workspace.tsx`,
  `components/preview/scene-preview.tsx`
- MCP production surface: `mcp/production/tools.ts`, `mcp/production/api-client.ts`

## 2) Authoring Chain (MCP -> REST -> persist)

`update_project` (`mcp/authoring/tools.ts:76`) input schema is
`{ projectId, project: projectPatchSchema }` where
`projectPatchSchema = z.record(z.string(), z.unknown())` (`mcp/authoring/tools.ts:18`)
and the client type is `type ProjectPatch = Record<string, unknown>`
(`mcp/authoring/api-client.ts:13`). The patch is passed through verbatim to
`PUT /api/projects/{id}` (`mcp/authoring/api-client.ts:283`).

Server side, `PUT` (`app/api/projects/[id]/route.ts:25`) calls
`applyProjectUpdate(existingProject, body)` (`lib/projects/project-update.ts:34`):

1. `collectProjectPatchShapeIssues(incoming)` — structural guard.
2. Shallow merge: `{ ...existingProject, ...incoming, id, createdAt, updatedAt }`
   (`project-update.ts:55-61`). **Only top-level keys are merged.**
3. `normalizeProject(...)` then `validateProject(candidate)`.
4. Invalid -> HTTP 422 `{ message, errors, warnings }`; valid -> persisted under
   the per-project lock.

Implication for overlays: because the merge is a shallow top-level spread and
`project.scenes` is a top-level array, **sending `scenes` replaces the whole
scene array** (`docs/hermes-mcp-manual.md:124`). Callers must resend complete
scene objects, including `id`, `order`, `type`, `visual`, `render`, `overlay`,
`narration`. Passing only `{}` leaves scenes untouched. Because `overlay` is a
nested value inside each scene object, `style`/`timing` reach the store only if
the full overlay object is present in that resent scene.

## 3) Field Preservation: does `style`/`timing` survive every layer?

`normalizeScene` (`lib/projects/normalize-project.ts:278`) sets
`overlay: scene.overlay ?? (scene.textOverlay ? {...} : { type: 'none' })`
(`:293`). It does **not** deep-normalize `overlay`; the object (including
`style`/`timing`) is passed through untouched, or replaced by `{ type: 'none' }`
when absent. So once an overlay object is supplied, P29.1's optional fields are
preserved verbatim into the stored `Project`.

| Layer | Location | Effect on `overlay.style` / `overlay.timing` |
| --- | --- | --- |
| MCP input schema | `mcp/authoring/tools.ts:18` | Pass-through (`z.record(z.unknown())`), no stripping |
| MCP client | `mcp/authoring/api-client.ts:283` | Sends patch unchanged as PUT body |
| REST PUT | `app/api/projects/[id]/route.ts:54-93` | Top-level shallow merge; `scenes[]` replaced |
| Shape guard | `lib/projects/project-patch-shape.ts:55` | Only checks `overlay` is an object; ignores nested `style`/`timing` |
| Normalize | `lib/projects/normalize-project.ts:293` | Overlay passed through as-is |
| Validate | `lib/validation/project-validation.ts:185` | Checks only `overlay.type` in `OVERLAY_TYPES` |
| Render plan | `lib/render/scene-resolver.ts` | Copies `scene.overlay` into the plan scene |
| Fingerprint | `lib/render/render-fingerprint.ts:29` | `overlay: scene.overlay` serialized whole -> `style`/`timing` included |
| Staleness | `lib/render/render-status.ts:56` | Completed render with a different fingerprint -> `stale` |
| Notes field | `normalize-project.ts:296` | `renders: []` preserved on resent scene (`:296`) |

Net: **the fields are authorable and persist today via REST/MCP.** But they are
never normalized or validated on write; P29.1 clamps/defaults them lazily at
render time (`resolveTextOverlay` in `lib/render/text-overlay.ts`).

## 4) Validation Gaps

`validateProject` only enforces the overlay discriminator:

```
if (scene.overlay && !OVERLAY_TYPES.includes(scene.overlay.type)) { ... error ... }
```
(`lib/validation/project-validation.ts:185-187`; `OVERLAY_TYPES` at
`lib/constants.ts:22`).

Consequences for the P29.1 fields:
- **`overlay.type` is effectively required whenever an overlay object exists.**
  A scene whose overlay omits `type` (e.g. only `style`) fails with
  `scene.overlay.invalid` (`OVERLAY_TYPES.includes(undefined) === false`).
- **`style` and `timing` are unvalidated.** Wrong-typed values (e.g.
  `style: "big"`, `style.fontSize: "huge"`, `timing.fadeInSeconds: "1"`) are
  accepted by the shape guard, persisted by normalization, and pass
  `validateProject` because neither layer descends into them. They only surface
  at render (clamped/defaulted/invalid-color fallback), so the API reports
  success for input the renderer will silently coerce.
- **No range checks**: `position`, `fontSize`, `margin`, `fadeInSeconds`,
  `fadeOutSeconds`, `color`, `box` are not constrained at authoring time.
- No `overlay.text` length or `overlay.data` shape check (pre-existing).

Where a fix belongs: `collectProjectPatchShapeIssues` should reject wrong
container types for `overlay.style` / `overlay.timing`, and `validateProject`
should range/type-check the scalar fields (and return the existing
`RenderIssue[]` error shape so MCP `VALIDATION_FAILED.details.errors` already
carries it, per `docs/hermes-mcp-manual.md:124`).

## 5) UI Gaps

`components/project/project-workspace.tsx:1528-1529` exposes only an Overlay
**type** select and an Overlay **text** field. There are no controls for
`fontSize`, `color`, `box`, `margin`, `fadeInSeconds`, or `fadeOutSeconds`.
`components/preview/scene-preview.tsx:152` only renders `overlay.text` (a static
preview; it does not apply the drawtext style). So the shipped P29.1 fields can
be authored only through the API/MCP, and the editor preview does not reflect
them. This is the primary authoring gap for a human operator.

## 6) Production / Render Propagation

Overlay edits correctly invalidate downstream rendering:
- `createSceneRenderFingerprint` serializes `overlay: scene.overlay` wholesale
  (`lib/render/render-fingerprint.ts:29`), so any `style`/`timing` change yields
  a new fingerprint.
- `deriveSceneRenderStatus` compares a completed render's stored
  `renderFingerprint` to the current one and returns `status: 'stale'` on
  mismatch (`lib/render/render-status.ts:56`, `:109-120`).
- `production-planner.ts` consumes `deriveSceneRenderStatus` and re-schedules a
  `scene_render` action for stale/not-rendered scenes (and `final_compose`
  remains gated on all scenes being current, via `deriveCompositionReadiness`).
- `deriveCompositionArtifactStatus` marks an existing composition stale when any
  scene render is stale (`render-status.ts:221-241`).

So editing `overlay.style` on a rendered scene flips it to **stale**, and the
next production run re-renders just that scene — which is exactly the desired
behaviour, with no extra wiring needed.

## 7) Deterministic Mock E2E Workflow (existing routes only)

All steps use already-shipped routes; `mode: "mock"` uses fake providers and
makes no paid calls. Keep background music out of this path (music is a separate
`manage_project_music` concern).

1. `POST /api/projects` (or MCP `create_project`) -> `projectId`.
2. `PUT /api/projects/{id}` (MCP `update_project`) with `project.scenes` = full
   array; each scene carries `overlay: { type: 'text', text, position,
   style: { fontSize, color, box, margin }, timing: { fadeInSeconds,
   fadeOutSeconds } }` and `scene.narration.text`.
3. `GET /api/projects/{id}/validation-report` (MCP `get_validation_report`) and
   `GET /api/projects/{id}/production-plan` (MCP `get_production_plan`) to
   confirm the scenes are renderable and to see planned actions.
4. `POST /api/projects/{id}/production-runs` with `{ mode: 'mock' }`
   (`app/api/projects/[id]/production-runs/route.ts:12-33`) -> run id.
5. Poll `GET /api/production-runs/{runId}` and
   `GET /api/production-runs/{runId}/log` (see
   `lib/client/production-run-client.ts:100,127`; MCP `get_run_status` /
   `get_run_log`).
6. Fetch a scene render via `GET /api/projects/{id}/renders/{renderId}/file`,
   or the final composition via
   `GET /api/projects/{id}/compositions/{compositionId}/file`.
7. Assert the produced scene MP4 decodes (overlay visible) and that re-sending a
   changed `style` flips the scene to `stale` in the next `production-plan`.

This is deterministic with fake providers and needs no new endpoints.

## 8) Recommendation / Implementation Proposal (phased, <=8 points)

1. **Nested shape guard** (`lib/projects/project-patch-shape.ts`): when
   `scene.overlay` is an object, require `overlay.style` / `overlay.timing`, if
   present, to be objects; emit `scene.overlay.style.invalid` /
   `scene.overlay.timing.invalid`. Cheap, prevents 500s and silent coercion.
2. **Runtime validation** (`lib/validation/project-validation.ts`): type/range
   check `overlay.type` (already), plus `position` enum, `fontSize` (24-220),
   `margin` (16-240), `color` (string), `box` (boolean), `fadeInSeconds` /
   `fadeOutSeconds` (finite, >= 0, bounded by scene duration or a cap). Reuse the
   existing `RenderIssue` error shape so MCP `VALIDATION_FAILED` already reports
   it.
3. **Shared constants** (`lib/constants.ts`): export the overlay style/timing
   bounds and reuse them in both the P29.1 renderer clamps and the new
   validators, so authoring and render agree (single source of truth).
4. **UI controls** (`components/project/project-workspace.tsx:1528`): add
   numeric inputs for `fontSize` / `margin`, a color input, a box toggle, and
   fade-in/out fields, shown only when overlay type is not `none`; PATCH back
   through the existing full-scene save.
5. **Preview parity** (`components/preview/scene-preview.tsx:152`): render the
   overlay text with the chosen font size/color/position so editors see the
   intent (static is sufficient; no need to reproduce drawtext exactly).
6. **MCP documentation** (`docs/hermes-mcp-manual.md`): document that
   `overlay.style` / `overlay.timing` are supported in the full-scene patch and
   list the accepted ranges; restate the wholesale `scenes[]` replacement rule.
7. **Deterministic test** (`tests/`): add a workflow test that authors overlays
   with style/timing via the update path, asserts they persist and validate,
   renders one scene, then asserts a style edit marks it stale. Reuse the
   existing mock/fake provider harness from the P29.1 integration tests.
8. **No new MCP tool required.** `update_project` already carries the fields and
   `get_scene` / `get_project` return them. P29.2 is validation + UI + docs +
   tests, not new surface area.

Ordering: (1)->(2)->(3) first (correctness, unblocks safe authoring), then (4)->(5)
(editor), then (6)->(7) (docs + regression), leaving (8) as the explicit
non-decision.

## 9) Explicitly Out of Scope

Auto captions, word-level timing, karaoke/ASS, global captions, AI video, new
paid services, provider pilot-gate changes, and any renderer changes beyond the
P29.1 drawtext path already shipped.
