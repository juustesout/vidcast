# P31.7 — Server-Side FFmpeg Concurrency Safety

Date: 2026-10-17
Scope: prevent another system-wide OOM by bounding simultaneous local FFmpeg
processes for scene rendering and final composition, without changing provider
behaviour, concat strategy, or unrelated pipeline code.
Status: implementation and verification complete. Nothing was committed.

## Verdict

1. **All local FFmpeg spawns now share one process-global slot.** Scene renders
   and every final-composition subprocess (normalize, concat, music mix) go
   through `runFfmpeg()`, which acquires the same keyed slot before spawning.
2. **The effective default is 1 concurrent FFmpeg process.** It can be raised
   only by the server operator through `FFMPEG_MAX_CONCURRENCY`, and only up to
   a hard ceiling of 4. A client cannot raise it.
3. **Client requests are clamped twice.** The HTTP and MCP schemas reject
   `scene_render`/`final_compose` above the hard ceiling with `400`, and the
   run service clamps direct/legacy requests to the active server limit before
   they are persisted as `acceptedConfig`.
4. **The live 3-scene mock run never had more than one FFmpeg process.** Out of
   104 `/proc` samples, 94 observed exactly one FFmpeg process and 10 observed
   none. No sample observed two or more.
5. **The hardening is process-local, not host-global.** The limiter lives on
   `globalThis` inside one Node.js process. It covers every route/module/run in
   that process, but it does not coordinate separate server processes, separate
   containers, or unrelated tools that spawn FFmpeg. That boundary is explicit
   below.

## Implementation

### Shared limiter

New `lib/render/ffmpeg-limiter.ts`:

- key: `ffmpeg:local-spawn`;
- environment variable: `FFMPEG_MAX_CONCURRENCY`;
- default: `DEFAULT_FFMPEG_CONCURRENCY = 1`;
- hard ceiling: `MAX_FFMPEG_CONCURRENCY = 4`;
- bounded waiter queue: `MAX_FFMPEG_QUEUE = 64`;
- strict integer parsing: only `^[0-9]+$` values in `1..4` are accepted;
  `2abc`, `+2`, `2.0`, `0`, `5`, and empty values fall back to 1;
- `withFfmpegSlot(operation, task)` acquires a slot before spawn;
- `getFfmpegLimiterStats()` exposes `{ limit, active, queued }`;
- `resetFfmpegLimiterForTests()` simulates a fresh process.

The limiter reuses the existing FIFO `withKeyedLimit()` implementation in
`lib/concurrency/keyed-limiter.ts`. That module gained:

- optional `KeyedLimitOptions.maxQueue`;
- `KeyedLimitQueueFullError`;
- `getKeyedLimitActiveCount()` and `getKeyedLimitQueueLength()`.

Existing provider callers keep the previous unbounded queue because they do not
pass `maxQueue`.

### Single spawn path

`lib/render/ffmpeg-executor.ts` now exports:

```ts
runFfmpeg(command, args, options, operation)
```

It wraps `runProcess()` in `withFfmpegSlot()`. The slot is acquired before the
child starts, so queue wait time does not consume the FFmpeg timeout budget.
`finally`-style release happens on success, failure, timeout, abort/error, and
process exit. A server restart discards the in-memory limiter state, so no slot
can survive a dead process.

Switched call sites:

- `lib/render/renderer.ts:391` — scene render → `runFfmpeg(..., 'scene_render')`;
- `lib/render/video-compositor.ts:181` — normalize → `runFfmpeg(..., 'final_compose')`;
- `lib/render/video-compositor.ts:237` — music mix → `runFfmpeg(..., 'final_compose')`;
- `lib/render/video-compositor.ts:247` — concat → `runFfmpeg(..., 'final_compose')`.

`ffprobe` remains outside the limiter because it does not decode frames and is
not the memory driver identified in P31.6.

### Server-side clamping

`lib/production/run-service.ts` adds `clampLocalFfmpegConcurrency()`. It is
applied to:

- default `scene_render` and `final_compose` limits;
- a run's `limits` override for those two action types;
- the no-override merge path.

The persisted `acceptedConfig.limits.perActionConcurrency` therefore never
exceeds the operator limit. If an older run is recovered after a restart with a
legacy high value, the spawn limiter still serializes its actual FFmpeg work.

Schema ceilings changed from `128` to `MAX_FFMPEG_CONCURRENCY` in:

- `app/api/projects/[id]/production-runs/route.ts`;
- `mcp/production/tools.ts`.

### Backpressure and observability

Waiters queue FIFO; there is no polling loop. If more than 64 operations are
waiting for the key, the next request fails with `KeyedLimitQueueFullError`
instead of growing memory without bound. Such failures surface as a failed
render action, not as an OOM.

When a request waits at least 1 second, the server logs:

```text
[ffmpeg-limiter] <operation> waited <n>ms for a slot (limit=..., active=..., queued=...)
```

No paths, asset names, prompts, or credentials are logged. The live 3-scene run
did not produce this line because its per-action concurrency was already 1, so
scene renders and composition phases did not contend; the log path is covered
by a unit test.

### Configuration

`.env.example` now documents:

```env
# FFMPEG_MAX_CONCURRENCY=1
```

No value is set in the workspace `.env`, so runtime verification used the safe
default of 1.

## Residual risks and explicit limits

1. **Process-local scope.** One Node.js process is protected. Two `next start`
   processes, a separate worker process, or a second container can each use the
   full limit, so host-wide concurrency can be `processes × FFMPEG_MAX_CONCURRENCY`.
   A host-global guarantee would require an OS-level semaphore or cgroup memory
   limit, which this change does not add.
2. **Only wrapped spawns are covered.** Any future direct `spawn('ffmpeg', ...)`
   or external script bypasses the limiter. `runProcess` remains exported for
   non-FFmpeg integrations; code review should keep FFmpeg on `runFfmpeg`.
3. **Other memory consumers are not bounded.** Node heap, Sharp image
   processing, providers, `ffprobe`, and the browser/dev server can still
   contribute to system pressure. P31.6 measured 140 Node processes at 3.75 GiB
   during the OOM; this fix addresses the FFmpeg multiplier only.
4. **Concurrency 1 reduces render parallelism.** That is intentional for the
   known 8-GB, 2-CPU, no-swap runtime. Raising `FFMPEG_MAX_CONCURRENCY` requires
   host-specific memory measurement.
5. **Composition re-encode memory remains.** P31.6 measured 532.3 MiB for the
   1080p concat re-encode and 62.8 MiB for a stream-copy variant. Stream-copy
   was out of scope here and remains the next optimization opportunity.
6. **Queue overflow is an action failure.** With the supported two-run, small
   scene shape the 64-waiter bound is far away. If it is ever reached, the
   affected action fails instead of piling up, which is the safer failure mode
   but not retried automatically.
