# P31.3 — Stale Composition After Real Stock Re-selection

Date: 2026-10-17
Scope: ensure a changed or re-generated scene render invalidates the existing final composition and re-plans `final_compose`, without adding fingerprint fields or changing provider routing.
Status: fixed, tested, live-verified with zero provider calls. No commit/push.

## Verdict

Confirmed cause: the composition fingerprint already records the render id used
for every scene, but `deriveCompositionArtifactStatus()` never compared that id
with the latest completed render. It only checked whether the scene render was
currently stale, plus narration, audio-mix, and music changes. After a scene was
re-rendered and became current, the old composition was therefore reported as
`current` and `final_compose` was skipped.

The fix compares the recorded `renderId` with the latest completed render id and
marks the composition stale on a mismatch. The existing planner path then
schedules `final_compose` automatically. No new fingerprint fields were needed,
and the P31.2 stock routing was not touched.

## Recon: how composition freshness works

1. The compositor builds the plan from the latest completed render of each scene
   (`lib/render/video-composition-service.ts:99`) and writes the render ids into
   `inputFingerprint.scenes[].renderId` (`:221`, `:238`).
2. `deriveCompositionArtifactStatus()` (`lib/render/render-status.ts:211`) walks
   the current scenes and compares scene freshness, narration signatures, audio
   mix, and music against the artifact.
3. It did not compare the recorded render id with the latest completed render id.
4. `deriveProductionPlan()` (`lib/production/production-planner.ts:171`) uses
   that status. When the status is `current`, `final_compose` is marked
   `current` and not executed (`:523`).
5. A re-render changes the render id and the render fingerprint. Until the
   composition is rebuilt, its fingerprint references the old render id.

The link between render regeneration and composition validity was missing; the
fingerprint input and artifact metadata were already sufficient.

## Fix

`lib/render/render-status.ts:235` now compares the fingerprint's render id with
`renderStatus.latestCompletedRender?.renderId`:

```ts
const currentRenderId = renderStatus.latestCompletedRender?.renderId;
if (currentRenderId && fingerprintScene.renderId !== currentRenderId) {
  reasons.push(`Scene ${scene.order} was re-rendered since the final composition was created.`);
}
```

Why this is the minimal fix:

- The composition fingerprint already contains `renderId`; no schema or field was
  added.
- `latestCompletedRender` is the same artifact selection used by the compositor
  (`lib/render/video-composition-service.ts:99`), so the comparison matches what
  a recomposition would actually use.
- Existing staleness reasons for stale renders, narration, audio mix, and music
  remain unchanged.
- The planner already knows how to turn a stale composition into a ready
  `final_compose` action; no planner change was required.

No stock, narration, or render reuse logic changed. Valid stock selections and
current renders are still reused.

## Residual risks

1. **Legacy compositions without a usable fingerprint cannot be validated by
   render id.** Compositions with no `inputFingerprint`, or with a `p10.1`
   fingerprint that has no entry for a scene, keep their previous behavior. They
   are still invalidated by other freshness checks, but a pure render-id change
   is not detectable. Adding a migration or backfill is a separate task; no
   fields were added here.
2. **Re-rendering with identical bytes still triggers recomposition.** The
   fingerprint records the render id, not a content hash. This trades a small
   amount of redundant work for guaranteed correctness. The planner only runs
   when the scene render is current, so it does not loop.
3. **Failed newer renders are handled by existing scene freshness checks.** The
   composition status already marks a scene with no current completed render as
   stale. The new comparison uses the latest completed render, matching the
   compositor, so it does not create an extra false positive.
4. **The live run remains unresolved without narration.** This is the expected
   fail-closed behavior for a scene with no narration text; the composition
   still completes. A narrated project would continue to a terminal completed
   run.
5. **Working tree is still uncommitted.** P31.2 and P31.3 changes plus the new
   reports and tests remain uncommitted. No commit or push was performed.
