# P31.2 — Stock Cache Mode Safety

Date: 2026-10-17
Scope: implement the P31.1 fix so a mock-mode stock selection can never be reused as a valid real-mode selection, and a real-mode run can never accept a fake selection.
Status: implemented, tested, live-verified. No commit/push. No paid image generation. Dev server stopped.

## Verdict

The mode-blind cache leak is fixed at three layers:

1. The router only accepts a cache hit when the cached provider is allowed for the
   current mode.
2. The stock selection service validates mode compatibility before treating an
   existing selection as current, rejects incompatible manual selections with an
   explicit error, and asserts the routed provider is allowed before persisting.
3. The production planner treats a stock selection as current only when it is
   valid for the run mode. Automatic invalid selections are re-planned even
   without `force: true`; manual invalid selections are blocked instead of being
   silently replaced.

Mock mode still never contacts a real provider. Real mode still never accepts a
fake selection. Valid manual selections remain pinned.

One separate issue was discovered during live verification and is documented as a
residual risk, not fixed here: an existing final composition is not invalidated
when a scene is re-rendered with a different asset (see Residual risks).

## Root cause recap

P31.1 established two mode-blind checks:

- `StockRouter.resolve()` returned the persistent cache entry before filtering by
  `allowedProviders`, so a `fake` entry produced by a mock run was returned
  verbatim in real mode (`lib/ai/stock/stock-router.ts`).
- `isSelectionCurrent()` and `hasUsableStockSelection()` ignored mode, so a
  non-forced real run skipped `stock_select` entirely.

The cache in `projects/_stock/stock-state.json` is cross-project and has no TTL.
The fix keeps the cache useful inside a mode and self-heals each query the first
time it is used in real mode; no cache purge is required.

## Implementation details

### 1. Router cache guard

`lib/ai/stock/stock-router.ts:140` adds:

```ts
private isProviderAllowed(providerId: StockProviderId): boolean {
  return !this.allowedProviders || this.allowedProviders.has(providerId);
}
```

`resolve()` now requires both a cached entry and an allowed provider
(`:155`). The routing loop and the re-resolution loop use the same helper
(`:164`, `:280`). The cache-hit diagnostic still reports `cache_hit`, so
observability is unchanged for valid hits.

### 2. Service defense in depth

`lib/generation/stock-image-service.ts:155` adds `isSelectionUsableInMode()`:

- mock: any persisted selection is usable (no provider contact, stable output);
- real: the provider must be in `allowedProviders`.

`selectSceneStockImage()` resolves the mode before checking the existing
selection (`:190`). An existing manual selection that is not usable in the
current mode throws `stock.selection.incompatible` (409) instead of being
overwritten (`:196`). The current check only runs for a usable selection.
After routing, the selected provider is validated again before persistence and
throws `stock.provider.notAllowed` (403) on violation (`:244`).

`selectSceneStockPhoto()` now resolves the mode and validates the requested
photo/provider before the current check, so an incompatible manual photo is
rejected consistently whether or not an asset already exists (`:288`).

### 3. Planner mode awareness

`lib/production/production-planner.ts:151` adds
`isStockSelectionAllowedInMode()`: real mode rejects `fake`; mock mode accepts
any provider. `DeriveProductionPlanOptions.mode` is optional so existing callers
that do not care about mode keep working (`:70`).

For `stock_image` scenes (`:309`):

- `usableForMode = usable && modeCompatible`;
- `pinnedManual` requires a usable, compatible manual selection;
- `incompatibleManual` (usable asset, wrong mode, manual origin) is `blocked`
  with an explicit reason;
- a usable but mode-incompatible automatic selection is `ready` with reason
  "not valid for this mode; re-selecting" even without `force`;
- compatible manual selections stay `current` even under force.

`lib/production/run-service.ts:746` and `lib/production/run-policy.ts:325` pass
the accepted policy mode into every plan, including the preflight plan, so the
preflight and the runner agree on what is actionable.

3. The scene was re-rendered with the new asset. Latest render:
   `render_28b40f63-67bb-4bbf-866b-87ed39e11c62`, source asset
   `asset_1f7be191-a0b2-4d6c-ae86-fb9e80ea2670` (Pixabay JPEG). The earlier fake
   render was `render_bd0a7c50-2a4b-4f43-8972-5dbecc4699f1`, source asset
   `asset_95d7c06b-b5a7-40a9-8855-cdb55029d795`.

The live script's assertion "stock_select was not skipped as current" failed, but
the events show this is a harness issue, not a product regression: iteration 1
emitted `action_completed stock_select`, and iteration 2 emitted

the next iteration correctly reports it as current. No second run was performed
to avoid another provider call.

The run ended `unresolved` because narration text is missing in this disposable
project (expected fail-closed behavior). That does not affect the stock selection

The forced real path was not re-run live to stay within the one-call budget. It
is covered by the router/service tests and by the P31.1 live baseline, where the
forced real run reused `fake`; the cache guard now rejects that entry.

## Residual risks

1. **Final composition can remain stale after a stock re-selection.** This is a
   pre-existing invalidation gap, observed in the live project. The composition
   created at 06:13:09 references the old fake render
   (`inputFingerprint.scenes[0].renderId = render_bd0a7c50...`), while the latest
   scene render is `render_28b40f63...`. `deriveCompositionArtifactStatus()`
   (`lib/render/render-status.ts:211`) checks scene freshness, narration, audio
   mix, and music, but not whether the recorded render id still matches the
   latest render. Because the new render is current, the composition was still
   reported as "current" and was not recomposed. A forced real run forces
   `final_compose` and would recompose; a non-forced real run over an existing
   mock composition can leave the old MP4 in place even though the scene asset is
   now real. Recommended follow-up (separate task): compare
   `inputFingerprint.scenes[].renderId` with the current render id and mark the
   composition stale when they differ.
2. **Rotate the Pixabay key.** The attached forensic report
   (`.monkeycode-tmp-files/24de9a5a-hermes_test_003_result-1.txt`) contains a
   Pixabay API key in plain text. Rotate it in the Pixabay dashboard and update
   `.env`.
3. **Lazy cache self-healing is intentional.** Other queries that still hold
   `fake` entries will be corrected on their first real-mode use. No manual cache
   purge is needed. If a real run still reports `fake`, check the provider
   configuration and the cache key.
4. **Planner mode compatibility is coarse.** The planner distinguishes only
   `fake` from non-fake; provider availability is enforced by the service and
   router. Reusing an existing real asset does not require network access, so
   this is safe.
5. **Mock mode reusing real selections is intentional.** Without force, a mock
   run keeps an existing real selection and makes no network call. With force,
   mock routing allows only `fake`, so the selection is regenerated locally.
