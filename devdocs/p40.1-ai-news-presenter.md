# P40.1 - Optional AI News Presenter Layer

## Verdict

Core P40.1 implementation is complete and verified in mock mode. Presenter generation is an optional scene layer on top of the existing narration/render/composition pipeline; projects without presenter settings are unchanged. No paid provider request was made and no real-avatar pilot was executed. The real pilot is intentionally blocked pending explicit approval and confirmation of current HeyGen API pricing.

## Implementation

### 1. Data model and authoring contract

- Added `Project.presenter` settings: enable flag, provider, avatar id, output format, per-scene layout, PiP position/width/margin, start offset, and hard spend guards.
- Added durable `Project.presenterClips`: per-scene provider status, attempt history, narration signature, duration, and generated asset reference.
- Added `CompositionPlan.presenter` and `inputFingerprint.presenterSignature`, so layout or clip changes invalidate stale compositions.
- Presenter is normalized, validated, and patchable through the existing project API/MCP paths. It is absent by default, preserving existing projects.
- Presenter freshness follows the existing narration signature: stale narration cannot be sent to a paid provider.

### 2. Provider layer

- New provider contract (`lib/ai/presenter/provider.ts`) for submit, status polling, and download.
- Mock provider generates a deterministic local clip through FFmpeg, returns one generating poll and then a generated clip, and supports explicit failure injection.
- HeyGen provider is the single real-provider candidate:
  - uploads the existing narration audio asset via `POST /v3/assets`;
  - submits an avatar video via `POST /v3/videos` with `type: avatar`, `audio_asset_id`, `output_format`, and output dimensions;
  - polls `GET /v3/videos/{id}`;
  - downloads the rendered video.
- The presenter never uses the avatar provider's own audio or TTS. Existing narration remains authoritative.

### 3. Production pipeline

- Added `presenter_submit` and `presenter_poll` actions after narration and before scene render/final compose.
- Submit waits for current narration and persists a `submitting` attempt before the provider call. If the process dies before a job id is stored, automatic resubmission is blocked as "submission unknown".
- Polls are repeatable across runner iterations. During verification this exposed a real runner bug: `presenter_poll` was deduplicated after one execution, so a run stopped with an unfinished job. Fixed by treating both `video_poll` and `presenter_poll` as repeatable poll actions and added a regression test.
- Per-scene locks prevent concurrent submissions; mock mode cannot poll a real provider job.
- Paid spend guard runs immediately before a real submit and counts already-paid attempts plus the proposed seconds/request. It blocks the request when the configured hard limit would be exceeded.

### 4. Composition and audio isolation

- Added a separate presenter overlay pass between scene concat and music mixing.
- Fullscreen mode scales/crops the presenter to the canvas.
- PiP mode scales to a configurable fraction of canvas width, places it at a configurable corner/margin, and trims/pads to the authored scene window.
- The presenter clip is generated once and reused across compositions; layout changes do not trigger regeneration.
- Base audio is preserved with `-map 0:a?`; presenter clip audio is never mapped into the output. Existing music mixing remains the final audio stage.
- Composition validation still checks output size, duration, audio presence, and MP4 container.

## Real provider and cost disclosure

Chosen pilot provider: HeyGen.

Reasons:

- accepts an existing audio asset instead of requiring a script;
- supports avatar and photo-avatar inputs;
- exposes asynchronous video submission/status/download;
- supports WebM output for matting-capable avatars.

Current limitations:

- transparency is avatar-dependent: WebM output alone is not sufficient, and the provider may reject WebM for avatars not trained with matting;
- uploaded audio is capped at 32 MB by the provider;
- the live v3 response shape and matting behavior have not been exercised against a paid account.

Pricing status (confirmed, self-serve API tier):

- Billing is prepaid USD wallet usage when authenticating with `x-api-key`.
- The provider currently submits the default v3 avatar engine, which is Avatar IV.
- Avatar IV custom video avatar: `$0.0805 / sec` at 720p/1080p.
- Avatar IV photo avatar: `$0.0385 / sec`.
- Avatar V custom video avatar: `$0.12 / sec` (custom video avatars only; not photo avatars).
- Avatar III custom video avatar: `$0.01 / sec`; photo avatar: `$0.0165 / sec`.
- Avatar creation, if a new avatar is required, is a separate charge (`$2.13` custom video avatar, `$1.32` photo avatar) and is not part of the render pilot.

Proposed paid pilot cost:

- One 3-second scene, one paid request, using the default Avatar IV custom video avatar.
- Expected video generation cost: `3 sec x $0.0805/sec = $0.2415`.
- If a photo avatar is used instead: `3 sec x $0.0385/sec = $0.1155`.
- If Avatar V is explicitly selected: `3 sec x $0.12/sec = $0.36`.
- No avatar-creation charge is assumed; an existing custom avatar must be supplied through `HEYGEN_AVATAR_ID`.
- No paid retries: the hard cap is one request, so the maximum expected pilot spend is `$0.2415` for the default Avatar IV path.
- Configured guardrail for the pilot remains one 3-second scene and a 60-second/1-request project ceiling.

## Residual risks

1. **HeyGen live contract**: v3 endpoints, status field names, download URL behavior, and WebM/matting support must be smoke-tested with an approved account before relying on them. Pricing above is confirmed, but engine selection and avatar type must remain fixed for the pilot.
2. **No live lipsync quality check**: mock verification proves orchestration and composition, not avatar visual quality or lipsync accuracy.
3. **Authoring surface**: presenter settings are available through project JSON/patch and MCP, but no dedicated presenter editor panel was added in this phase.
4. **Polling bound**: presenter polling is bounded by overall run iterations rather than a dedicated presenter-poll counter; a stuck provider job eventually stops as unresolved.
5. **Transparency claim**: the provider advertises WebM support but rectangular PiP does not require alpha; true background removal remains unverified.
6. **Paid budget accounting**: failed paid attempts count toward the budget. This is intentionally conservative but may require an operator override policy later.
7. **No dollar-aware guard**: the hard guard limits seconds and requests, not USD. At the confirmed Avatar IV rate, the current 60-second default ceiling corresponds to `$4.83` per request; any future rate change should be reflected in the preflight report.
