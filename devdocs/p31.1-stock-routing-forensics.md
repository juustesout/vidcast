# P31.1 — Stock Provider Routing Forensics

Date: 2026-10-17
Scope: diagnose why a `stock_image` scene persisted `selection.provider: "fake"` during a `run_production({ mode: "real", force: true })` run while a real provider was configured.
Status: recon complete. No production code changed. No commit/push.

## Verdict

Primary root cause: the cross-project persistent stock selection cache is
**mode-blind**. `StockRouter.resolve()` returns a cached selection **before** it
checks `allowedProviders`, so a fake selection written by an earlier mock run is
reused verbatim by a later real-mode run. Pixabay was never contacted because the
router short-circuited on the cache; this was not a provider failure.

Secondary root cause: freshness checks are also mode-blind. A fake `origin:
"auto"` selection is treated as "current" for a real-mode run that does not pass
`force: true`, so the planner skips `stock_select` entirely and the renderer
keeps using the fake PNG asset.

The user's hypotheses were partly right but need refinement:

| Hypothesis | Verdict |
| --- | --- |
| A. Router falls back to fake | **Refined, confirmed as the leak.** There is no provider-failure fallback to fake. The leak is a stale cache hit that bypasses the allowed-provider filter. |
| B. `stock_select` was skipped | **False for the forced real run, true for the non-forced run.** The forced run did re-execute `stock_select` (selectedAt advanced) but received fake from cache. The non-forced run skipped `stock_select` because fake was considered current. |
| C. `providers.image: "openai"` conflicts | **Ruled out.** The `stock_select` path never reads `providers.image`. Stock is a separate modality; only `mode` is passed. |

This also means the MP4 can be technically valid while its visual content is not
real: the fake provider returns decodable PNG bytes, and the renderer has no way
to distinguish them from a real stock asset.

## Root cause detail

### 1. Cache hit happens before the mode/provider filter

`lib/ai/stock/stock-router.ts`:

```ts
const key = stockSelectionKey(query, request.orientation);
const cached = await this.store.getCachedSelection(key);
if (cached) {
  return { selection: cached, cached: true, diagnostics: [...] };
}

const order = this.resolveOrder(request.preferredProviders);
...
for (const providerId of order) {
  if (this.allowedProviders && !this.allowedProviders.has(providerId)) {
    diagnostics.push({ provider: providerId, outcome: 'skipped_not_allowed' });
    continue;
  }
```

Mock mode runs with `allowedProviders: ['fake']`
(`lib/generation/stock-image-service.ts:98-103`). After a successful fake
selection, the router writes the fake selection into the shared state store
(`lib/ai/stock/stock-router.ts:221-224`). A later real-mode router has
`allowedProviders = ['unsplash','pexels','pixabay']`, but the cache branch returns
the fake selection before that list is consulted.

### 2. The cache is global, persistent, and has no TTL

`FileStockStateStore` reads and writes `projects/_stock/stock-state.json`
(`lib/ai/stock/stock-state-store.ts:204`, `lib/storage/storage-paths.ts:50`).
The cache map is stored as-is with no timestamp, no mode, and no expiry
(`lib/ai/stock/stock-state-store.ts:47-51`, `:284-294`). Consequences:

- A fake selection survives process restarts.
- The cache is shared by every project, so a mock run in project X can poison a
  real run in project Y for the same `orientation::query` key.
- The key contains only orientation and normalized query
  (`lib/types/stock.ts:101-104`); it has no provider or mode dimension.

The existing state file is direct evidence of the mechanism: it contains
`landscape::mountain sunset => provider: fake` written at
`2026-10-16T10:08:51.090Z`, alongside seven real Pixabay entries. Any real-mode
auto selection for that query would reuse the fake entry.

### 3. The auto path never revalidates the provider after routing

In the manual selection path, the provider is checked against the resolved mode
before persisting (`lib/generation/stock-image-service.ts:278-281`). The auto path
has no equivalent check: it persists whatever the router returned
(`lib/generation/stock-image-service.ts:216-224`, `:308-361`). A cached fake
selection therefore reaches `persistSceneSelection`, which calls
`provider.fetchPhoto()` on the fake provider and saves a synthetic PNG as a normal
stock asset (`lib/generation/stock-image-service.ts:318-333`). That is exactly the
`mimeType: "image/png"` fingerprint in the user's report.

### 4. Freshness is mode-blind (non-forced runs)

`hasUsableStockSelection` only checks that a selection exists and its asset is
available (`lib/production/production-planner.ts:122-140`). It does not know the
run mode or the selection's provider. The planner therefore treats a fake auto
selection as "current" when `force` is false
(`lib/production/production-planner.ts:314-317`), sets `execute: false`, and the
service is never called. This is why run 3 in the user's report rendered stale
fake frames instead of re-selecting.

The service has the same issue: with `regenerate: false`, it returns the existing
selection before resolving the mode (`lib/generation/stock-image-service.ts:173-185`)
and calls `resolveStockMode` only afterwards (`:191`).

## Force semantics (verified)

| Case | Planner result | Executed | Notes |
| --- | --- | --- | --- |
| Auto selection + `force: true` | `execute: true`, `payload.regenerate: true` | yes | Fake is not pinned. Confirmed live: `selectedAt` advanced. |
| Manual selection + `force: true` | `execute: false`, reason "Manual stock image selection is pinned." | no | Preserved (`lib/production/production-planner.ts:296`, `:314-317`). |
| Auto selection + `force: false` (real mode) | `execute: false`, reason "Stock image selection is current." | no | Mode-blind; fake is silently accepted. |
| Manual selection + `force: false` | `execute: false` | no | Pinned. |

So `force: true` does re-run auto selections. The bug is not that force was
ignored; it is that the re-run resolved to fake.

## Fallback audit

- Mock mode is locked to `['fake']`; real providers are never contacted
  (`lib/generation/stock-image-service.ts:98-103`). Verified by test.
- There is no `catch` block that substitutes the fake provider. Real provider
  failures produce diagnostics and, if nothing succeeds,
  `StockRoutingError('ALL_PROVIDERS_FAILED')`
  (`lib/ai/stock/stock-router.ts:181-231`). The service converts that to
  `StockImageSelectionError` with code `stock.routing.failed`
  (`lib/generation/stock-image-service.ts:209-213`).
- Explicit fallback between real providers is allowed: unconfigured, quota-blocked,
  rate-limited, auth-failed, empty, or errored providers are skipped in order, and
  the next allowed real provider is tried. Verified by test.
- The only path that admits fake into real mode is the cache hit. Fixing the cache
  guard closes it without removing legitimate real-provider fallback.

## Proposed minimal fix

### Fix 1 (required): make the router cache mode/provider-aware

`lib/ai/stock/stock-router.ts` — only accept a cache hit when its provider is
allowed for this router:

```ts
const cached = await this.store.getCachedSelection(key);
if (cached && (!this.allowedProviders || this.allowedProviders.has(cached.provider))) {
  return { selection: cached, cached: true, diagnostics: [...] };
}
```

Why minimal: the cache stays useful for repeated selections within the same mode,
and a real selection overwrites the fake entry for that query when it is next
resolved. No destructive cache purge is needed. A fake entry remains valid for
mock mode.

### Fix 2 (required): defense in depth in the selection service

`lib/generation/stock-image-service.ts`:

- Resolve the mode before the "current" short-circuit, not after it.
- Treat an existing selection as current only if its provider is in
  `allowedProviders`.
- After `router.resolve()`, assert `allowedProviders.includes(selection.provider)`
  before persisting, mirroring the existing manual-path guard at `:278-281`.
- If the incompatible existing selection is `origin: "manual"`, fail explicitly
  with a new code (for example `stock.selection.incompatible`) instead of
  silently overwriting author intent. For `auto` selections, re-select normally.

This closes the leak even if a future router change reintroduces an invalid cache
hit, and it stops a direct service call (or direct API call without `mode`) from
persisting a disallowed provider.

### Fix 3 (required for non-forced runs): make stock freshness mode-aware

- Add an optional `mode?: RunMode` to `DeriveProductionPlanOptions`
  (`lib/production/production-planner.ts:60`).
- In `hasUsableStockSelection`, a `fake` selection is not usable when
  `mode === 'real'`.
- For `origin: "auto"`, mode-incompatible means `execute: true` with
  `payload.regenerate: true`.
- For `origin: "manual"`, mode-incompatible means `blocked` with an explicit
  reason (never silently overwrite the pinned manual choice).
- Inject the accepted policy mode in `run-service`'s `derivePlan` wrapper
  (`lib/production/run-service.ts:742`) and in the preflight plan
  (`lib/production/run-policy.ts:325`).

### Acceptance criteria

1. After a mock run, a real `force: true` run for the same query selects a real
   provider (Pixabay in this environment) and increments the Pixabay event
   counter by one; it never persists `provider: "fake"`.
2. After a mock run, a real run without `force` re-executes `stock_select` for
   auto selections instead of reporting "current", and does not render the fake
   asset.
3. A manual selection is never silently replaced; an incompatible manual fake
   selection in real mode produces an explicit error/blocked reason.
4. If all real providers fail, the run records an explicit `stock.routing.failed`
   (or blocked/unresolved action) and never falls back to fake.
5. Mock mode remains network-free and locked to fake.
6. All existing tests plus the 3 red P31.1 tests pass.

### Deliberately not proposed

- Adding `mode`/provider to the cache key: correct but creates parallel cache
  universes and still needs the allowed-provider guard.
- Adding a TTL to the cache: useful hygiene, but a fresh fake entry would still be
  reused in real mode. It does not fix the bug.
- Purging the current state file: unnecessary after Fix 1 and would discard quota
  accounting. The cache self-heals per query on the next real selection.

## Side observations (not the root cause)

- **Run status route can lag in Next dev.** During the first reproduction attempt,
  `GET /api/production-runs/:id` returned `running` with an intermediate summary
  after the persisted run JSON had already reached `unresolved`. A later request
  returned the correct terminal state. This looks like a dev-server module-instance
  artifact. It is why the reproduction script polls the persisted run JSON. It
  should be re-checked in a production build before treating it as a bug.
- **MCP `limits` has no `stock_select` key.** The run start schema accepts
  `image_generate`, `video_submit`, `video_poll`, `narration_generate`,
  `scene_render`, and `final_compose`
  (`app/api/projects/[id]/production-runs/route.ts:37-46`). Stock concurrency is
  controlled by `PRODUCTION_RUN_CONCURRENCY_STOCK` (default 2). This did not
  affect the bug, but it means a caller cannot tune stock_select per run.
- **The attached forensic report contains a provider API key in plaintext.** The
  value is not reproduced here. Treat that key as exposed, rotate it in the
  Pixabay account, and keep secrets out of reports and chat transcripts.
