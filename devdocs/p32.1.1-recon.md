# P32.1.1 Recon: narration end-padding margin review

Status: recon only for P32.1.1. No code changed in that phase, no dependencies added, no paid provider calls.
Builds on the uncommitted P32.1 scene-timing work (`lib/render/scene-timing.ts`).

## 0. Implementation status (P32.1.2)

Option B has now been implemented. `resolveSceneTiming` adds the end padding only when
`narrationDuration > authoredDuration`; renderer, render status, render plan and
composition share `sceneDurationMatches` (`0.15 s` floor, `2 / fps`);
`resolveMeasuredNarrationDuration` is the single measured source and returns the largest
persisted value. P32.1 had not shipped, so no production render migration was needed.
Section 2 below documents the pre-P32.1.2 rule for context.

## 1. Verdict

Before P32.1.2, the fixed `0.25 s` end padding was safe (speech was never trimmed) but it
was applied unconditionally to every narration, including narration that already fit in
its authored scene. As a result:

- A scene was extended by up to `0.25 s` whenever `narration + 0.25 s > authored duration`,
  even when the narration itself fit (`narration <= authored`). The old regression example
  was `0.8 s` narration in a `1.0 s` scene resolving to `1.05 s`
  (`tests/video-composition-plan.test.ts:363`).
- A narration that was legal on its own could be rejected at the `600 s` cap by the padding
  alone: `599.9 s` narration in a `600 s` scene resolved to `600.15 s` and failed
  `scene.narration.duration.exceedsMax` (`lib/render/scene-timing.ts:82`,
  `lib/render/scene-resolver.ts:240-248`).

Recommendation: replace the unconditional margin with **conditional padding** (option B):
add the `0.25 s` only when the narration does not fit the authored scene. This was
implemented in P32.1.2 before release, so no production migration was needed.

## 2. Pre-P32.1.2 rule (for context)

`lib/render/scene-timing.ts:60-92`:

```
required  = narrationDuration === undefined ? 0 : narrationDuration + 0.25
effective = max(authoredDuration, required, MIN_SCENE_DURATION_SECONDS)
adjusted  = effective > authoredDuration
exceedsMax = effective > MAX_SCENE_DURATION_SECONDS
```

- Measured narration source: `scene.narration.duration`, then the linked audio asset's
  `duration` (`lib/render/scene-timing.ts:42-58`).
- The only consumer that computes timing is `resolveRenderPlan`
  (`lib/render/scene-resolver.ts:236-264`). Planner, renderer and compositor all read the
  resolved `RenderPlanScene.duration`.
- `MIN_SCENE_DURATION_SECONDS = 0.1`, `MAX_SCENE_DURATION_SECONDS = 600`
  (`lib/constants.ts`).
- The compositor pads audio to the resolved scene duration with `apad=pad_dur=<duration>`
  and trims containers with `-t <duration>` (`lib/render/video-compositor.ts`,
  `buildNormalizeArgs`). It never adds silence beyond the timeline itself.

## 3. Findings

### 3.1 Extension quantifies to a narrow band plus the necessary case

With `d` = authored duration and `n` = measured narration:

- `n <= d - 0.25`: no extension (authored pacing preserved).
- `d - 0.25 < n <= d`: extension of `n + 0.25 - d` (between `0` and `0.25 s`), although the
  narration fits.
- `n > d`: extension of `n + 0.25 - d` (necessary extension plus `0.25 s`).

So the margin is not just "breathing room on auto-extension"; it also changes scenes whose
timing was already sufficient. The visible symptom is a slightly longer scene and a
one-time stale render, not a correctness failure.

### 3.2 The cap check can reject a legal narration

Validation and the render plan both compare `effectiveDuration` to `600 s`
(`lib/validation/project-validation.ts:296-308`, `lib/render/scene-resolver.ts:240-248`).
A narration of `599.9 s` is within the limit, but `599.9 + 0.25 = 600.15 s` is not, so the
project becomes invalid and the scene cannot render. This is a direct consequence of
padding before the cap check.

### 3.3 The compositor already handles the end gap deterministically

`apad` fills the segment to the resolved duration and `-t` bounds the output. No speech is
cut because `effective >= n` in every option below. The only difference between options is
how much silence follows the last word:

- A: `0.25 s` after an extended scene, and up to `0.25 s` of invented hold in the fit band.
- B: `0.25 s` after an extended scene, `0` invented hold when the authored scene already
  fits.
- C: `0` after an extended scene; the final word lands at the scene boundary.

### 3.4 Two duration sources are compared in the composition guard

`resolveMeasuredNarrationDuration` prefers `narration.duration` and only falls back to
`asset.duration` (`lib/render/scene-timing.ts:47-57`). However
`resolveNarrationAudioPath` compares the raw `asset.duration` to the resolved scene duration
(`lib/render/video-composition-service.ts:123`). If the measured record and the asset
metadata disagree, the timing gate and the composition guard can disagree. This is
defense-in-depth today because effective timing is normally derived from the same value, but
it is an avoidable second source of truth.

### 3.5 Render tolerance is inconsistent with the timeline tolerance

- `sceneDurationMatches` uses `max(0.15 s, 2 / fps)` (`lib/render/scene-timing.ts:94-99`).
- `renderer.ts` validates the produced file against the expected duration with
  `max(0.25 s, 1 / fps)` (`lib/render/renderer.ts:333`).

At 30 fps, a render at `expected + 0.20 s` passes output validation but is immediately
considered stale by `deriveSceneRenderStatus` (`lib/render/render-status.ts:57-68`) and is
rejected by composition (`lib/render/video-composition-service.ts:196-200`). The two
tolerances should come from one source.

### 3.6 Tests encode the current margin in three places

- Unit expectations: `7.75`, `7.25`, `10.75` and `3.35`
  (`tests/p32.1-scene-timing.test.ts:128-190`). All of these have `n > d`, so they remain
  valid under B and C.
- Composition fixture: scene `1.0 s`, narration `0.8 s`, render `1.05 s`
  (`tests/video-composition-plan.test.ts:363`). This is the only fixture that exists *only*
  because of the unconditional margin; under B it becomes scene `1.0 s`, render `1.0 s`.
- The test named "fails when linked narration audio is longer than scene duration"
  (`tests/video-composition-plan.test.ts:390-441`) now fails earlier, because the render is
  `1 s` while the resolved scene is `5.25 s` (`sceneDurationMatches` fails). It no longer
  exercises the narration-overflow guard, so the name is misleading.

## 4. Options

Let `d` = authored duration, `n` = measured narration, `p = 0.25`, `min = 0.1`,
`max = 600`.

| | Rule | Invented hold when narration fits | Padding on extended scenes | `600 s` false positive | Extra total duration |
|---|---|---|---|---|---|
| **A (current)** | `max(d, n + p, min)` | up to `p` in `(d - p, d]` | `p` | yes | `sum(max(0, n + p - d))` |
| **B (conditional)** | `n > d ? max(d, n + p, min) : max(d, min)` | none | `p` | no (if `d <= max`) | `sum(n > d ? n + p - d : 0)` |
| **C (no padding)** | `max(d, n, min)` | none | `0` | no | `sum(max(0, n - d))` |

Trade-offs:

- **A** is already implemented and tested. It is the most conservative against clipped
  speech, but it changes authored pacing in the fit band, can reject legal long narration,
  and adds duration that the user did not ask for.
- **B** keeps the breathing room exactly where the scene had to grow, preserves authored
  pacing when the narration fits, and removes the cap false positive. Implementation is a
  few lines in `resolveSceneTiming`; the `adjusted` and `formatSceneTiming` output already
  describe the result correctly.
- **C** is the smallest change and the most predictable, but a scene that grows to fit a
  long narration ends exactly on the last syllable. Given that TTS output often includes
  trailing silence, `0.25 s` on grown scenes is reasonable and worth keeping.

## 5. Recommendation

Adopt **B** before P32.1 is committed:

```
const narrationRequiredDuration =
  narrationDuration === undefined
    ? 0
    : narrationDuration > authoredDuration
      ? narrationDuration + endPaddingSeconds
      : 0;
const effectiveDuration = Math.max(authoredDuration, narrationRequiredDuration, minDurationSeconds);
```

Rationale:

1. No speech is ever trimmed; `effective >= narration` still holds in every branch.
2. Authored scene pacing is preserved whenever it is already sufficient.
3. The `600 s` false positive disappears for legal narration that fits its authored scene.
4. Total video duration only grows where the narration genuinely requires it.
5. Because P32.1 has not shipped, there is no second migration wave. If A ships and B is
   adopted later, scenes with `n > d - 0.10` that were re-rendered at A durations would
   become stale again under the `0.15 s` match tolerance.

Keep the `0.25 s` value as a named constant; it is a creative choice, not a technical
requirement. If a project-level setting is added later, B is the natural default.

## 7. Impact

### Existing renders

- If B is adopted before release: no production impact; no render has been produced against
  A outside local test runs.
- If A ships first and B follows: renders for scenes with `n > d - 0.10` and `n <= d` were
  stored at `n + 0.25`; B expects `d`. The difference is `> 0.15 s` in that sub-band, so those
  scenes become stale a second time and require re-render. Scenes with `n > d` already need a
  re-render under both options, so their impact is identical.
- Unchanged in all options: a render whose duration disagrees with the resolved timeline is
  stale (`lib/render/render-status.ts:57-68`) and composition refuses it
  (`lib/render/video-composition-service.ts:196-200`).

### Total video duration

- A: `sum(max(0, n + 0.25 - d))` over narrated scenes. Up to `0.25 s` per scene is invented
  even when the narration fits.
- B: `sum(n > d ? n + 0.25 - d : 0)`. Growth is limited to scenes that genuinely need it.
- C: `sum(max(0, n - d))`. No end gap on grown scenes.
- Music is trimmed/looped to the final timeline during composition, so a shorter total only
  reduces the required track length; it does not break the music path.

## 8. Residual risks / open questions

- `0.25 s` is arbitrary. It is added on top of whatever trailing silence the provider already
  emitted, so the audible gap can be larger than `0.25 s`. If that becomes a problem, the
  longer-term fix is trimming trailing silence during the narration analysis step, not
  reducing the pad blindly.
- `adjusted` and `formatSceneTiming` expose the extension, but the workspace UI only warns
  when `asset.duration > scene.duration` (`components/project/project-workspace.tsx:1799-1803`).
  Under B the UI copy stays correct; under A it does not mention the invented hold.
- The renderer/composition tolerance mismatch (section 3.5) is independent of the margin and
  should be fixed in the same change or tracked separately.
- If per-project padding is added later, option B's conditional rule should remain the
  default so authored pacing is not silently overridden.
- No paid calls were made and no provider behavior was assumed beyond the existing
  `maxDurationSeconds` usage (`lib/generation/narration-service.ts`,
  `lib/ai/text-to-speech/fake-provider.ts`).
