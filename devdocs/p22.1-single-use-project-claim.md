# P22.1: Single-use project claim capability - implementation report

Status: **implemented and verified.** A service-created (ownerless) project is
now claimable only by the holder of a server-minted, single-use claim token.
No commit or push.

This builds on P22 (`p22-secure-claim-and-immutable-ownership.md`), which made
ownership immutable through generic updates but deliberately shipped **no** claim
endpoint because there was no trusted authorization basis. P22.1 adds exactly
that basis: possession of a capability created by the trusted server and
delivered over the trusted service channel.

---

## 1. Mechanism

1. When a **service** caller creates a project (`POST /api/projects`), the server
   mints a high-entropy `claimToken` (32 random bytes, base64url), stores only
   its SHA-256 **hash** plus an expiry in a sibling `claim.json`, and returns the
   raw token **once** in the 201 response. User-created projects are unaffected:
   they are owned immediately and get no token.
2. The agent (Hermes/MCP) passes the token to the intended user out-of-band.
3. `POST /api/projects/{id}/claim` (user session only; a service token is
   rejected) verifies the presented token against the stored hash in constant
   time, then **atomically** under the per-project keyed lock assigns
   `ownerId = identity.subject` and consumes the token.

The token is never placed in a URL, never persisted in raw form, and never
returned by any project read.

---

## 2. Fail-closed behavior

| Situation | Result |
| --- | --- |
| Valid user session + correct, unexpired token, ownerless | `200`, owner assigned, token consumed |
| Project already owned | `409 CONFLICT` (`claim.alreadyClaimed`) |
| Unknown project id | `404 NOT_FOUND` |
| Missing / wrong / expired token, or no capability | `403 FORBIDDEN` |
| Service token (bearer) | `403 FORBIDDEN` |
| No identity | `401 UNAUTHENTICATED` |
| Replayed token after success | Project now owned -> `409` |

A malformed expiry is treated as expired. Two concurrent redemptions cannot both
win: the ownership check, token verification and ownership write all run under
the same project lock.

---

## 3. The token is now the only path to an ownerless service project

Adding a capability is meaningless if the old id-based first-claim paths still
work, so those now **skip any project with a pending claim**:

- `requireProjectAccess` legacy first-claim (`lib/security/access-control.ts`).
- `getProjectForIdentity` page-level legacy claim (`lib/security/page-access.ts`).
- `claimUnownedProjects` bulk claim on new-session creation
  (`lib/storage/project-store.ts`).

Projects created by `createProject` (tests, sample seed) carry no claim record,
so their behavior is unchanged. Only service-created claimable projects are
protected. Service identities still bypass ownership checks as before.

---

## 4. Surface changes

- `POST /api/projects` (service): response now `{ project, claimToken }`.
- `POST /api/projects/{id}/claim` (new route): body `{ token }`, returns
  `{ project }` on success.
- MCP `create_project`: `CreateProjectResponse.claimToken?` is populated when the
  API returns one; the tool description documents the out-of-band hand-off and
  the claim endpoint. The read-only MCP server reuses the same authoring service,
  so it inherits this automatically.
- UI: a minimal claim form on `/projects` (project id + token, token submitted in
  the request body only, never the URL).

## 7. Remaining risks / follow-ups

1. **Token delivery is out-of-band and unauthenticated by design.** Security
   rests on the service channel not leaking the token (MCP output, logs). The
   token is short-lived and single-use, which bounds the damage.
2. **Confidentiality, not discovery.** A service-created project is hidden from
   every browser list until claimed (unchanged from P22); the user must receive
   both the project id and the token.
3. **No dedicated throttle on `/claim`.** The 256-bit token space makes online
   guessing infeasible; a per-identity throttle could be added later.
4. **Multi-process deployments.** The claim/ownership lock is in-process
   (`withKeyedLock`), consistent with the rest of the store; a future
   multi-instance deployment would need a cross-process lock.
5. **`claimUnownedProjects` on new session** still bulk-claims genuinely
   ownerless, claim-free projects (pre-existing, first-caller-wins).
