# P31.6 — FFmpeg Composition Memory Forensics

Date: 2026-10-17
Scope: determine whether an FFmpeg composition used about 7.1 GiB of memory,
why the kernel OOM-killed an FFmpeg process, and what the smallest safe fix is.
Status: recon only. No production code was changed, and nothing was committed.

## Verdict

1. **No single composition or FFmpeg process used 7.1 GiB.** The highest peak
   measured for one process at 1080p was **532.3 MiB RSS** (final concat
   re-encode); normalize and scene-render peaks were 518.7 MiB and 492.5 MiB.
2. **The 7.1 GiB figure was system-wide usage, not process usage.** At the only
   kernel OOM on this host, the sum of all task RSS values was **7.37 GiB** of
   **8.00 GiB** RAM, with **100 MiB free**, **zero swap**, and no effective
   memory cgroup limit. Seven concurrent 1080p `scene_render` FFmpeg processes
   accounted for 2.62 GiB; 140 `node` processes accounted for 3.75 GiB.
3. **The OOM happened during concurrent scene rendering, not during final
   composition.** The affected run requested `scene_render: 8` (seven scenes
   were rendered at once) and started those renders at 12:48:12. The kernel
   killed one FFmpeg process at 12:55:50. Final composition was never reached
   by that run.
4. **The unsafe input is accepted by the API.** The start schema allows
   `scene_render` up to 128, and `mergePerActionLimits()` clamps requested
   overrides to 64 rather than to the service default/max. The code default is
   1, and the environment default is at most 8.
5. **Composition itself is memory-heavy but not the root cause.** The concat
   step re-encodes the already-normalized 1080p segments (532.3 MiB, 64.08 s).
   A video-stream-copy variant with the same audio limiter used 62.8 MiB and
   0.72 s in a synthetic same-segment test. That is a worthwhile separate
   optimization, but it would not have prevented this OOM.
6. **The previous P31.4 note misattributed the OOM.** The P31.4 fixture run used
   `scene_render: 1` and `final_compose: 1`, its composition ran sequentially,
   and the reproduced peak for that 10-scene shape was 532.3 MiB. The OOM block is from 2026-10-16 12:55:50, one
   day before the P31.4 run (2026-10-17 14:12–14:15), and belongs to the P29
   project/run described below.

## Correlated run

`projects/project_ba439064-e936-409b-9ec7-cc38bee1dbb3/runs/run_055484b7-7f36-4ccd-8a9b-d26614da5869.json`

- project: "This Week in Dev & AI — Episode 1", 7 scenes x 7 s, 1920x1080, 30 fps;

- accepted per-action concurrency:

- run started 12:47:59; seven scene renders scheduled/started 12:48:12;

  at 12:56:01; run ended `failed`, with 11 failed and 1 waiting action;
- later compositions in the same project succeeded at 13:10:14 and 13:39:51

The killed PID cannot be mapped to a specific scene from dmesg alone, but the

## Pipeline and measured stages

Code path: `final_compose` action -> `VideoCompositionService.composeProject()`
-> `LocalFFmpegVideoCompositor.compose()` -> `runProcess()`.

The compositor normalizes each scene **sequentially** into
`<tempDir>/normalized-NNN.mp4`, then concatenates them in one FFmpeg invocation:

- `lib/render/video-compositor.ts:295` — sequential normalize loop;
- `lib/render/video-compositor.ts:304` — concat output;
- `lib/render/video-compositor.ts:145` — concat applies the limiter only to audio;
- `lib/render/video-compositor.ts:250` — output validation/probe.

Normalize invocation for 1080p:

```text
ffmpeg -y -i <scene-render.mp4> [-i <narration.wav> | -f lavfi -i anullsrc=...]
  -vf "scale=1920:1080:force_original_aspect_ratio=increase,crop=1920:1080,fps=30,format=yuv420p"
  -filter_complex "[...]atrim=0:6.000,apad=pad_dur=6.000,aresample=48000,aformat=channel_layouts=stereo,volume=1.000[aout]"
  -map 0:v:0 -map [aout] -t 6.000
  -c:v libx264 -pix_fmt yuv420p -c:a aac -b:a 192k -movflags +faststart
  <tempDir>/normalized-NNN.mp4
```

Concat invocation:

```text
ffmpeg -y -f concat -safe 0 -i <tempDir>/concat-list.txt
  -af "alimiter=limit=0.95:level=false"
  -c:v libx264 -c:a aac -pix_fmt yuv420p -r 30 -movflags +faststart
  <output.mp4>
```

Measurements were taken by sampling `/proc/<pid>/status` (VmRSS, VmHWM,
VmSize, Threads) and `/proc/<pid>/smaps_rollup` (Pss) every 50 ms, plus
`/proc/meminfo`. A safety brake killed the measured child if `MemAvailable`
fell below 200 MiB. No OOM was induced deliberately.

| Stage | Output | Peak RSS | Peak PSS | Threads | Wall time |
| --- | --- | ---: | ---: | ---: | ---: |
| Single scene render, 1080p | 6 s | 492.5 MiB | - | 12 | 9.66 s |
| Normalize, 1080p | 6 s | 518.7 MiB | 516.6 MiB | 14 | 7.53 s |
| Normalize, 1080p, `-threads 2` | 6 s | 491.2 MiB | 489.0 MiB | 14 | 7.30 s |
| Normalize, 1080p, filter+encoder thread caps | 6 s | 491.4 MiB | 489.2 MiB | 13 | 7.01 s |
| Normalize, 720p | 6 s | 296.4 MiB | 294.2 MiB | 18 | 5.21 s |
| Concat re-encode, 1080p | 60 s | 532.3 MiB | 530.1 MiB | 12 | 64.08 s |
| Concat video-copy + audio limiter, 1080p | 60 s | 62.8 MiB | 60.6 MiB | 3 | 0.72 s |
| Music mix, video copy + AAC audio | 60 s | 56.9 MiB | 54.7 MiB | 5 | 4.00 s |

All ten sequential 1080p normalizes were stable at 516.8–518.6 MiB RSS and
6.41–7.30 s each. The 1080p concat output was valid H.264/AAC, 60.038 s,
1920x1080, 30 fps, 517,276 bytes. The 720p output was 1280x720. The copy-concat
test used the same 6 s segment repeated ten times, so it validates the memory
shape and arithmetic, not distinct-segment timestamp behaviour.

Host at recon time: 7,965 MiB RAM, 0 swap, 2 CPUs, FFmpeg 5.1.9-0+deb12u1,
libavfilter 8.44.100. The container has no delegated memory cgroup:
`/sys/fs/cgroup` exposes no `memory.current`, `memory.max`, or `memory.peak`,
so there is no per-container hard cap to absorb an overrun. At recon time
`free` already showed 6,674 MiB used and 1,291 MiB available with 146 `node`
processes (4,207 MiB RSS). That baseline, not composition, is why the host is
close to the edge even before a render starts.

## Root cause

The OOM was **aggregate overcommit**, not a leak or a single huge allocation:

```text
7 x concurrent FFmpeg scene renders   ~2.6-3.6 GiB
140 x node processes                  ~3.75 GiB
opencode/next/esbuild/other           ~0.95 GiB
                                      -----------
                                      ~7.3-8.3 GiB vs 8.00 GiB, no swap
```

The per-action limit was raised by the run request. `executeBounded()` launches
`limit` actions with `Promise.allSettled()` (`lib/production/production-runner.ts:235`),
so `scene_render: 8` means up to eight 1080p FFmpeg processes at once. The
service's own default of 1 never applied because the request supplied 8.

The API permits this:

- `app/api/projects/[id]/production-runs/route.ts:43` accepts `.max(128)`;
- `lib/production/run-service.ts:183` clamps overrides with hard-coded `.max(64)`
  instead of the configured service maximum;
- `lib/production/run-service.ts:146` defines the safe default as 1 (env max 8);
- `lib/production/run-service.ts:153` allows two runs at once.

Even two runs at the configured defaults can overlap one render each, and a run
at `final_compose: 2` can overlap two concat re-encodes. There is a per-project
composition lock (`lib/render/video-composition-service.ts:24`), but no global
FFmpeg concurrency or memory limiter.

## Smallest safe fix

Priority 1: **make the server authoritative about FFmpeg concurrency.**

- Clamp requested `scene_render` to the configured server maximum, not 64.
  Reject or silently clamp values above it; do not accept a client-supplied 8
  on an 8 GiB host.
- Add a process-wide FFmpeg semaphore shared by all runs and actions. A
  conservative starting point for this host is two FFmpeg children; a
  memory-aware admission check should require at least about 600 MiB of
  `MemAvailable` per 1080p child (plus headroom) before starting another.
- Keep `scene_render` at 1 and `final_compose` at 1 by default. Two concurrent
  1080p children already cost about 1.0 GiB, which is close to the current
  host's 1.29 GiB available before any baseline growth.
- Tests: requested limit above server max is clamped; global semaphore is
  respected across two runs; a simulated child signal (`SIGKILL`) marks the
  action failed with a signal/OOM-style reason instead of success.

Priority 2, separate optimization: **stop re-encoding the video during concat.**
The normalized segments already share codec, resolution, fps, and pixel format.
Use `-c:v copy` and keep the audio filter/re-encode for the limiter. The
synthetic test went from 532.3 MiB / 64.08 s to 62.8 MiB / 0.72 s with a valid
60.038 s 1080p30 H.264/AAC file. This must be validated with ten distinct
segments, narration, music, and the AAC priming/timestamp checks before it is
adopted. It reduces composition peak but does not prevent the scene-render OOM.

Not recommended as the primary fix:

- `-threads 2` or filter-thread caps: 518.7 -> 491.2 MiB, a 5% reduction only.
- Rendering at 720p internally and upscaling: 296.4 MiB (43% lower), but it is a
  visible quality change and needs product approval.
- Relying on the kernel: there is no swap and no usable memory cgroup in this
  deployment, so the kernel's only response is global OOM.

## Failure handling and artifacts

- A child killed by a signal is classified as `signal` by `runProcess()`
  (`lib/render/ffmpeg-executor.ts:113-131`) and mapped to `FFMPEG_FAILED` by the
  renderer/compositor. A missing or empty output is caught by `validateOutput()`
  (`lib/render/video-compositor.ts:250`).
- In this OOM the runner recorded **timeout** for all seven scenes, not a
  signal/OOM reason. The killed PID was one of the same batch, so the evidence
  suggests the OOM kill was masked by the timeout path (or by a scene-timeout
  override). Operators cannot rely on the run event alone to identify an OOM.
- `validateOutput()` calls `probeMedia()` without mapping `FFprobeError` to
  `OUTPUT_INVALID` (`lib/render/video-compositor.ts:256`,
  `lib/render/ffprobe.ts:26`). A partial/corrupt file can therefore escape the
  compositor's `VideoCompositionError` contract and surface as a raw probe
  error. It is still marked as a failed action by the runner, but with less
  useful classification.
- Temp cleanup is correct on normal errors (`finally` removes the per-render and
  per-composition temp directory). It cannot run when the Node process itself is
  SIGKILLed. Leftovers exist from the interrupted P31.4 composition:
  `.tmp/composition_fb618384-.../` with ten normalized segments and a 48-byte
  `final-composition_fb618384-....mp4`. Total `projects/` usage is only 71 MB,
  so this is a cleanup/bookkeeping issue, not a memory issue.

The OOM itself should not be reproduced on this shared host. If it must be
studied, use an isolated VM with a memory cgroup and no other workloads.

## Open questions and missing measurements

- No `/proc/meminfo` snapshot exists from 12:55:50; the OOM task table and
  meminfo block are the only historical evidence.
- The killed PID's command line and parent were not captured; the scene mapping
  is inferred from timing, PID contiguity, and the seven-scene batch.
- The server's `RENDER_SCENE_TIMEOUT_MS` at 12:48 is unknown; the 469 s failure
  delay is not the 60 s default and suggests an override.
- The copy-concat variant was not validated with ten distinct segments,
  narration, music, or `-movflags +faststart` on a real project. It is a
  candidate, not a verified production change.
- No 4K or 720p full-composition peak was measured; 720p was normalized only.
- Production `next start` and serverless process isolation were not tested.

## Recommendation

Implement the concurrency clamp and global FFmpeg limiter first. They are small,
testable changes that directly remove the OOM trigger. Treat the concat
stream-copy change as a second, separately validated optimization. Do not
change render resolution or thread counts as the primary mitigation; the
measurements show they are either ineffective or a quality trade-off.

No code was changed and no commit was made in P31.6. Awaiting approval before
implementing the concurrency fix or updating the P31.4 note.
