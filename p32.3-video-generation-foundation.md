# P32.3 - Provider-neutral video generation foundation

## Verdict

Implemented and verified. Video generation now resolves through one typed, server-side capability contract before an attempt is persisted or an external provider is called. Existing `local`/fake, OpenAI and FAL integrations keep their transport/lifecycle behavior, but provider identity, credentials and model/mode compatibility are validated centrally. Ambiguous paid submits no longer unlock a second submit.

Full suite: 118 files / 924 tests green. Typecheck, lint and production build clean. No provider calls were made in tests and nothing was committed or pushed.

## What changed

### New central modules

- `lib/ai/video-generation/catalog.ts`
  - Single provider vocabulary: `openai`, `fal`, `local` (`fake` is an alias only at the boundary).
  - Real-provider classification, credential-env mapping and provider-to-`GenerationProvider` normalization.
- `lib/ai/video-generation/models.ts`
  - Client-safe model authoring hints. The FAL suggestion list moved here from `lib/constants.ts`; constants re-exports it, so existing imports keep working.
- `lib/ai/video-generation/capabilities.ts`
  - `VideoGenerationMode = text_to_video | image_to_video | reference_guided`.
  - `VideoGenerationCapabilityContract` (provider, model, mode, capabilities).
  - `resolveVideoGenerationCapabilityContract()` validates the mode, reference roles/count, aspect ratio, duration and model-aware capabilities.
- `lib/ai/video-generation/resolver.ts`
  - `resolveVideoGeneration()`: policy -> adapter -> model-aware capabilities -> validated request.
  - `resolveVideoGenerationProviderForAttempt()`: strict poll/cancel resolution; an active attempt without provider identity is refused instead of falling back to a server default.

### Provider contract

- `VideoGenerationProvider` gained optional `getCapabilitiesForModel(model?)`.
- FAL implements it: the endpoint suffix now decides the mode.
  - `.../image-to-video`: image-to-video only.
  - Any other valid endpoint: text-to-video only.
  - Generic references stay unsupported for both.
- Fake capabilities no longer advertise a closed duration enum it never enforced. Local generation still accepts any positive scene duration.
- Registry, run policy, forwarding and the scene inspector now use the catalog instead of separate provider lists/checks.

### Service and recovery

- `submitSceneVideoGeneration()` uses the resolver before persisting the attempt.
- Every attempt records `metadata.idempotencyKey = attemptId` (and the key is also passed to the adapter metadata).
- The busy guard now blocks any active attempt, including an active attempt without a provider job id.
- Ambiguous real-provider submit failures stay `queued` with `providerStatus: submit_unresolved`, no job id, and `metadata.submitUnresolved`.
- `reconcileInterruptedGenerations()` marks an unconfirmed submit failed even when an older asset exists, and suppresses automatic retries in real mode.
- Polling an unconfirmed submit without a job id now returns a clear `generation.attempt.submitUnresolved` error instead of a generic missing-job-id 500.

## Central decision rules

1. The server config is the only authority for mock/real mode. A caller may request a provider/model, never a mode.
2. Mock mode rejects `openai`/`fal` before the adapter is resolved; real mode requires the provider credential in the catalog mapping.
3. Unknown providers are rejected by the resolver; malformed FAL model ids are rejected by model-aware capability resolution.
4. The request mode is derived from reference roles, then checked against the provider/model capabilities.
5. Capability validation happens before the queued attempt is written and before `provider.submit()`.
6. Poll/cancel reuse only the provider persisted on the attempt; `other`/missing is an error, never a fallback.
7. Routes and UI only forward provider/model. No provider-specific validation branches remain in routes or the scene inspector.

## Capability matrix

| Provider | Model source | text_to_video | image_to_video | reference_guided | Reference limit | Aspect ratios | Duration | Cancel |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `local` (fake adapter) | ignored | yes | yes | yes | 8 | 16:9, 1:1, 9:16 | any positive (scene duration) | no |
| `openai` | stored/request model, provider default fallback | yes | yes | yes | 8 | 16:9, 1:1, 9:16 | provider-defined | no |
| `fal` text endpoint | arbitrary valid `<owner>/<model>[...]`, default from env | yes | no | no | frames only (0 for text) | 16:9, 1:1, 9:16 | 1-15s (adapter, before fetch) | yes |
| `fal` image endpoint | must end in `image-to-video` | no | yes | no | max 1 start + 1 end frame | not an input | 1-15s (adapter, before fetch) | yes |

Validation specifics:

- A FAL text endpoint with keyframes is rejected as `UNSUPPORTED`.
- A FAL image endpoint without frames is rejected as `UNSUPPORTED`.
- A FAL image endpoint with an ordinary style reference is rejected as `REFERENCE_ERROR`.
- A provider with `maxReferences` rejects excess references.
- A provider with a declared aspect/duration enum rejects values outside it.
- Durations must be finite and positive for every provider.

## Rejection before the external request

These cases are rejected before `provider.submit()`:

- unknown provider id;
- real provider requested in mock mode;
- missing `OPENAI_API_KEY` / `FAL_KEY` in real mode;
- malformed FAL endpoint (URLs, traversal, invalid characters);
- model/mode mismatch for FAL;
- unsupported mode for the provider;
- plain references where only keyframes are supported;
- too many references;
- unsupported aspect ratio or declared duration enum;
- non-positive duration.

The FAL adapter still performs its own final duration and frame-role checks inside `submit()`, but those checks run before the `fetch` call.

## Idempotency, retries and recovery

Existing safeguards reused:

- per-scene submit lock prevents concurrent submissions;
- per-attempt poll lock serializes polls and cancellation;
- the attempt is persisted before the provider call;
- transient poll failures keep the attempt active with the same job id;
- failed cancel attempts keep the attempt active and resumable;
- run lock/store dedupe prevents duplicate batch execution;
- recovery resumes stored job ids by polling and never resubmits them.

New safeguards:

- `metadata.idempotencyKey` is durable and correlates the submit with its attempt.
- Any active attempt blocks a new submit, even without a job id.
- Submit failures are split into:
  - definitive (`NOT_CONFIGURED`, invalid/unsupported/reference errors, auth, rate limit, provider rejection): mark failed as before;
  - ambiguous (`PROVIDER_FAILED`, transport timeout/abort, unknown errors from a real provider): keep active/unconfirmed.
- An ambiguous submit is never auto-retried. Recovery fails it and suppresses the real-mode `video_submit`, so a restart cannot bill a second job. An older asset may remain attached for rendering, but the unconfirmed generation is surfaced as failed.
- A crash after provider acceptance but before the job id is persisted lands in the same unconfirmed-submit recovery path.

Known limits:

- OpenAI and FAL do not expose a documented provider-side idempotency key. The metadata key is recorded, but duplicate prevention is enforced by this service's state machine, not guaranteed by the provider.
- If a provider accepted a request and the response was lost, the service cannot recover the remote job id. That attempt must be resolved manually (or reconciled in the provider dashboard) after the local status is reset.
- An unconfirmed live attempt intentionally blocks the scene until restart recovery or a manual status reset. This is the deliberate trade-off for avoiding a second paid submit.

## Residual risks

- OpenAI model ids are opaque. The resolver trims and forwards them but cannot reject an unknown-but-well-formed OpenAI model before the request; the provider remains the authority. A future model catalog (or allowlist) can be added without changing routes/UI.
- FAL accepts arbitrary valid endpoint ids by design. The foundation enforces shape and mode consistency, not a fixed commercial allowlist. This preserves existing custom-endpoint behavior.
- FAL duration bounds (1-15s) live in the adapter, not in the capability contract, because the contract has no min/max duration fields. They are still checked before the fetch.
- Capability metadata is maintained per adapter. A new provider must implement `getCapabilitiesForModel()` correctly and add itself to the catalog.
- Manual status edits can still intentionally force a retry of an unconfirmed attempt. That is an explicit user action, not an automatic retry.
- No provider-side idempotency guarantee exists, as noted above.

## Proposed next provider integration

For the next provider (for example one video model family), the only required work should be:

1. Implement `VideoGenerationProvider` and model-aware `getCapabilitiesForModel()`.
2. Add the provider key and credential env var to `catalog.ts`.
3. Add any model suggestions to `models.ts`.
4. Add adapter tests, including the capability contract and ambiguous-submit behavior.
5. Add the provider to the existing `VIDEO_GENERATION_PROVIDERS` UI list only if it is approved for authoring.

No route, service, recovery or UI validation changes should be needed. A provider-side idempotency header, if offered, should be added inside that adapter using the existing `metadata.idempotencyKey`.
