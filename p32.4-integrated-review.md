# P32.4 - Integrated review of the P32 changeset

## Verdict

**READY TO COMMIT.** The three P32 chains work as one changeset, the integrated mock production renders and composes a decodable MP4, and the full suite is green. No provider calls were made and nothing was committed or pushed.

- `npm run typecheck`: clean
- `npm run lint`: clean
- `npm run build`: clean (Next.js 15.5.27)
- `npm test`: **118 files / 929 tests passed** (~163 s)

Two state-machine bugs and one preview/render parity issue were found during the review and fixed in this phase. No architectural changes were made.

## Integrated chain verified

### Narration -> timeline -> render -> composition

1. Narration is generated without a scene-duration cap; the measured duration is persisted on the narration record and the linked audio asset.
2. `resolveSceneTiming()` keeps the authored duration when narration fits, and only extends it to `narration + 0.25 s` when narration is longer. A scene is never shortened.
3. `resolveRenderPlan()` is the single source of scene durations, render fingerprints, timeline length, music length and composition input.
4. The renderer writes the plan duration; readiness marks renders stale when the recorded duration differs from the plan outside `max(0.15 s, 2/fps)`.
5. Composition rejects a render whose duration does not match the plan instead of silently cutting narration.
6. The browser preview now shows and fades the overlay against the same effective duration as the renderer.

### Music -> timeline -> composition

1. The production run derives the requested track length from the authoritative timeline, not the historical 60 s default; an explicit run-plan length still wins.
2. The compositor loops a short track (`-stream_loop -1`), trims it to the timeline and fades it out at the end.
3. The music asset id is part of the composition fingerprint, so changing the track invalidates an existing composition.

### Video resolve -> submit -> poll -> cancel -> recovery

1. One server-side resolver owns mode, credentials, provider identity and model-aware capabilities.
2. Capability rejection happens before the attempt is persisted and before `provider.submit()`.
3. Poll/cancel reuse only the provider persisted on the attempt; missing/`other` is refused instead of falling back to a possibly different paid provider.
4. Ambiguous submits stay queued/unconfirmed and are never auto-retried; recovery fails them and suppresses the real-mode action.
5. A recovered attempt is a fresh attempt: attempt-scoped failure flags no longer leak into it.

## Findings and fixes

### 1. Attempt-scoped failure flags leaked into a retry (fixed)

`submitSceneVideoGeneration()` built the new `queued` attempt with `...current.metadata`, which carried `submitUnresolved`, `pollUnresolved`, `lastPollErrorCode` and `cancelFailed` from the previous attempt into a clean retry. The retry could then look unconfirmed or poll-failed before any provider call.

`previousMetadata` now removes those four flags while keeping the durable `idempotencyKey` (which is replaced by the new attempt id). Regression test: `tests/video-generation-service.test.ts` - "clears attempt-scoped failure flags when a recovered attempt is retried".

### 2. Unflagged real-mode submits were treated as resumable (fixed)

The unconfirmed-submit branch in `reconcileInterruptedGenerations()` only triggered when `metadata.submitUnresolved === true`. A hard crash during the submit (before the catch handler writes the flag) left an active video attempt with no job id, which was not suppressed and could be resubmitted.

In `real` mode, an active `generated_video` attempt without a provider job id is now always unconfirmed (a video render cannot exist without an external submit). It is marked failed with `PROVIDER_FAILED`/`submit_unresolved`, and the real-mode `video_submit` action is suppressed. Mock restore-from-asset behaviour is unchanged. Tests: `tests/run-recovery.test.ts` - both new recovery cases.

### 3. Preview used the authored duration (fixed)

`components/preview/scene-preview.tsx` displayed `scene.duration` and resolved overlay fades with `scene.duration`. After P32.1 a narration-extended scene renders longer, so the preview disagreed with the renderer. It now uses `resolvedScene?.duration ?? scene.duration` for the duration chip and the shared overlay resolver. Test: `tests/scene-preview.test.tsx` - "previews the narration-extended duration instead of the authored duration".

## End-to-end evidence

New test in `tests/production-run-e2e.integration.test.ts`:
"runs an integrated mock production with narration-driven timing, timeline music and render reuse".

Fixture: three generated scenes - image scene authored at 2 s with 6.0 s of fake-TTS narration, then a generated-video scene and an image scene at 3 s each; mock music policy.

Observed and asserted:

- timeline = **12.25 s** (6.25 + 3 + 3); scene 1 `timing.adjusted = true`, narration 6.0 s
- every scene has one completed render matching the plan duration within tolerance; scene 1 render > 6 s
- music requested for **12,250 ms** (the timeline), not the 60 s default; music asset spans the timeline
- composition uses the music asset and is within 0.3 s of the timeline
- composition probe: **H.264, 640x360, AAC**, decodes without FFmpeg errors
- second run completes without `action_completed`, `video_poll_completed` or `composition_completed`; render ids and the single composition are reused

## Migration and regression notes

- No P32.x build has been committed, so there is no production data migration. Projects on disk are unchanged; the new timing is derived at read/plan time.
- Existing renders whose duration differs from the new timeline by more than the tolerance are now stale and re-render once. This is intended and only affects scenes whose narration extends the authored duration.
- Legacy **active** video attempts with a missing or `other` provider can no longer be polled/cancelled and need a manual state reset. This is the deliberate safety trade-off; the state was only reachable through the old fallback.
- Disabling real providers while a paid job is still active blocks its poll/cancel too (pre-existing policy gate). Resolve such jobs before flipping the flag, or in the provider dashboard.
- FAL's 1-15 s duration bounds remain adapter-enforced and are not exposed by the capability contract; invalid durations are still rejected before the network call.
- An ambiguous real submit intentionally blocks the scene until restart recovery or a manual reset; this is the documented P32.3 trade-off.
